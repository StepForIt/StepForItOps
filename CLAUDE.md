# CLAUDE.md — StepForIt Ops

Plateforme de gestion, versioning, vérification et monitoring de workflows n8n (multi-instances).

## Stack

- **Langage** : TypeScript partout (strict).
- **Backend** : NestJS (`apps/api`) + Prisma + PostgreSQL.
- **Frontend** : Next.js (App Router) + Refine + Ant Design (`apps/web`).
- **Monorepo** : pnpm workspaces. `packages/core` (domaine + ports), `packages/adapters/*` (implémentations des systèmes externes).
- **Infra** : Docker + docker-compose (postgres, api, web).

## Commandes

```bash
pnpm install                  # installer les dépendances
pnpm --filter @nwm/api prisma:generate   # générer le client Prisma
pnpm --filter @nwm/api prisma:migrate    # créer une migration (dev)
pnpm dev:api                  # API en watch (port 3001)
pnpm dev:web                  # Web en watch (port 3000)
pnpm test                     # tests (core + api + web ; l'api demande DATABASE_URL_TEST, cf. ci-dessous)
pnpm typecheck                # tsc --noEmit sur tout le workspace
pnpm lint                     # ESLint (0 avertissement toléré)
pnpm format                   # Prettier sur tout le dépôt (`format:check` en CI)
docker compose up -d          # tout lancer (postgres + api + web) en DEV avec hot reload
docker compose up -d --build  # seulement si package.json / pnpm-lock.yaml ont changé
docker compose restart api    # après modification de apps/api/prisma/schema.prisma
```

Les tests de `apps/api` écrivent dans une base **jetable**, jamais celle de dev : les suites vident ses tables entre deux cas, et `test/helpers/db.ts` refuse de tourner sur une base dont le nom ne finit pas par `_test`. Une fois pour toutes :

```bash
docker run -d --name nwm-test-pg -e POSTGRES_USER=nwm -e POSTGRES_PASSWORD=nwm \
  -e POSTGRES_DB=nwm_test -p 55444:5432 postgres:16-alpine
export DATABASE_URL_TEST=postgresql://nwm:nwm@localhost:55444/nwm_test
```

Un contrôle nouveau se pose au niveau le MOINS cher qui puisse l'attraper : une règle dans `packages/core` (pur, joué en secondes), ce qu'un service persiste dans `apps/api/test`, et seulement ce qui n'existe qu'assemblé — un garde, un filtre d'exception, une pagination — au bout en bout. Un parcours navigateur qui vérifie une règle de domaine coûte mille fois son prix et casse pour mille raisons étrangères.

Ils vivent à **deux niveaux**. Les tests de SERVICE instancient leur cible à la main (`new WorkflowSyncService(prisma, …)`) : l'hexagonal les rend joignables sans conteneur, les collaborateurs étant des ports, donc des objets qu'on fournit (`test/helpers/fakes.ts`). Les tests de BOUT EN BOUT (`app.e2e.spec.ts`) démarrent l'application entière et lui parlent en HTTP — c'est le seul niveau où existent le garde de jeton, celui des modules désactivés, la traduction des erreurs Prisma et la pagination Refine : un service rend un objet, ce qui arrive au navigateur est décidé après lui. Tous les ports sortants y sont remplacés par une doublure qui **échoue** en nommant le port et la méthode (`strictPort`), pour qu'un appel réseau involontaire se voie au lieu de passer pour un test vert ; et les crons sont arrêtés après le démarrage, sinon les cinq qui tournent à la minute frapperaient ces doublures au milieu d'un test.

Les **parcours de bout en bout** (Playwright, `apps/web/e2e/`) vont plus loin : un navigateur, la console, l'api et la base. C'est le seul niveau qui traverse le proxy `/backend/*`, le middleware d'authentification et le dataProvider Refine — trois choses qui vivent ENTRE le front et l'api, et qu'aucun test des deux côtés ne voit. Playwright démarre lui-même l'api compilée et `next dev`, pose le schéma et le jeu d'essai (`apps/api/scripts/seed-e2e.mjs`, qui vit là parce que Prisma y est généré) :

```bash
pnpm --filter @nwm/web exec playwright install chromium   # une fois
DATABASE_URL_TEST=… pnpm --filter @nwm/web test:e2e
```

Un **faux fournisseur d'IA** (`apps/web/e2e/fake-anthropic.mjs`) sert le tour de l'assistant : une vraie clé dans la CI, ce serait un appel facturé et non déterministe à chaque exécution. Rien n'est branché dans le code applicatif pour cela — le SDK Anthropic lit `ANTHROPIC_BASE_URL` de lui-même, et c'est la configuration Playwright qui la pose sur l'api. Un **faux n8n** (`apps/web/e2e/fake-n8n.mjs`) est démarré avec la stack et sert exactement les workflows du jeu d'essai : la console appelle n8n plus souvent qu'il n'y paraît — une recherche restée sans résultat déclenche une synchro, un export repart de la source —, et une instance pointée sur un port fermé rendait ces chemins imprévisibles, la liste se vidant ou se remplissant selon le moment.

L'authentification y est ACTIVE, contrairement au dev local : la connexion est le premier parcours de tout le monde, et `AUTH_OPTIONAL=1` la rendrait invisible. Les parcours sont volontairement peu nombreux — ce qui casse là doit être ce qui casse la console entière, un composant se teste moins cher. Deux pièges rencontrés, réglés dans le code des tests : le `Segmented` d'antd fait glisser une pastille par-dessus ses libellés, et un clic — même `force` — part à des COORDONNÉES que le navigateur remet à la pastille, qui n'écoute rien (l'événement se pose donc sur l'input radio lui-même, `dispatchEvent`) ; et Refine repousse les paramètres de liste dans l'URL après le rendu, si bien qu'un clic lancé pendant ce remplacement part dans un nœud déjà remonté — c'est ce remplacement qu'on attend, jamais `networkidle`, que le websocket de `next dev` empêche d'arriver.

La **CI** (`.github/workflows/ci.yml`) joue quatre jobs sur chaque PR vers `dev`, et chacun tient ce qu'aucun autre ne voit :

| job | ce qu'il attrape |
|---|---|
| `typecheck · tests · build` | format, lint, `tsc --noEmit` sur tout le workspace, les tests, et les deux builds. `prisma generate` vient AVANT le typecheck : sans le client, la moitié des services ne compile pas et l'échec ne parlerait pas du code |
| `migrations · schéma` | `migrate.sh` — le script du conteneur `migrate` de la prod, joué tel quel sur une base neuve — puis `prisma:check`. Le premier compare la BASE au schéma, le second les MIGRATIONS : une migration éditée à la main après coup ne se voit que par le second |
| `image api · démarrage à blanc` | le build de l'image de prod, dont la dernière couche joue `smoke-boot.sh` : une dépendance importée mais non déclarée compile, passe le typecheck, et meurt au boot de l'arbre `--prod` — en silence quand c'est un module métier |
| `parcours · navigateur` | les parcours Playwright, avec postgres et Chromium seul |

Le format et le lint sont les premières étapes du premier job, avant même `prisma generate` : ils ne demandent ni client ni build, et une PR qui n'a qu'une virgule de travers doit l'apprendre en trente secondes, pas en quatre minutes. Un test de flakiness ne se conclut jamais sur une passe : les parcours se rejouent trois fois de suite (en local, ou en relançant le job) avant d'être déclarés stables, et un correctif de test se juge à la MUTATION — neutraliser la règle visée dans le code doit faire tomber ce cas-là, et lui seul.

**Lint et formatage** sont séparés et ne se marchent pas dessus : Prettier décide de la MISE EN FORME (`.prettierrc.json` : guillemets simples, point-virgules, largeur 110 — le style déjà écrit, pas un défaut), ESLint du RESTE (`eslint.config.mjs`). `eslint-config-prettier`, posé en dernier, éteint les règles stylistiques d'ESLint : deux outils qui se disputent l'indentation ne produisent qu'une file de conflits. Pas d'analyse typée non plus — `tsc --noEmit` tourne déjà partout, et les règles typées coûteraient un projet TypeScript par paquet pour redire la même chose. Ce qu'ESLint attrape, lui seul : un import mort, un `any` (le dépôt n'en a aucun hors frontière de bibliothèque, chacun portant son exception nommée), un hook React sous condition. La documentation est hors de Prettier : il y recomposerait tableaux et listes sans rien apporter. Le formatage initial (331 fichiers) est dans `.git-blame-ignore-revs` — `git config blame.ignoreRevsFile .git-blame-ignore-revs` une fois par clone, GitHub le lit tout seul.

En local, `docker-compose.override.yml` est chargé automatiquement : images au target `dev` (nest --watch / next dev) avec les sources montées en bind mount → **pas besoin de rebuild pour voir les changements de code**. `docker-compose.yml` est la prod telle quelle (aucun port publié, variables sensibles requises) : l'override ne fait qu'y ajouter les ports, le hot reload, et retirer le conteneur `migrate`. En prod : `docker compose -f docker-compose.yml`.

Les images de prod sont taillées pour un déploiement rapide, et cela contraint deux choses. Le web est bâti en `output: 'standalone'` : la config Next — dont le rewrite `/backend/*` → `API_INTERNAL_URL` — est **figée au build**, elle se pilote par build arg et non par variable d'environnement au runtime. L'api n'embarque plus que son `dist` et un arbre `--prod` construit à partir des seuls `package.json` (stage `prod-deps`) : **un package ajouté à `pnpm-workspace.yaml` doit y être listé**, et `prisma` est une dépendance de production parce que le conteneur `migrate` joue les migrations au déploiement. Les couches vont du plus stable au plus volatil, pour qu'un déploiement sans changement de dépendances ne réexporte que quelques Mo. Dernière couche de l'image api : un **démarrage à blanc** (`apps/api/scripts/smoke-boot.sh`) qui refuse le build si un paquet importé n'est pas déclaré dans `apps/api/package.json` — le typecheck ne voit que les types, et une dépendance seulement transitive compile puis meurt au boot de l'arbre `--prod`. Le contrôle porte sur le **specifier** et non sur l'échec : un module métier dont le dossier a été supprimé échoue sur un chemin relatif et reste toléré, quand un nom de paquet manquant bloque — y compris dans un module métier, où `loadFeatureModules` l'avalerait en warning et démarrerait la plateforme amputée sans que rien ne soit rouge.

## Schéma de base de données

Le schéma vit dans `apps/api/prisma/schema.prisma`, et **toute modification part avec sa migration** (`apps/api/prisma/migrations/`). En dev, l'api au target `dev` applique encore le schéma par `prisma db push` — pratique pour itérer, mais qui ne laisse aucune trace : une migration oubliée ne se voit qu'au déploiement.

En prod, un **conteneur `migrate`** joue `apps/api/scripts/migrate.sh` puis rend la main ; l'api ne démarre qu'après lui (`depends_on: service_completed_successfully`) et ne touche plus jamais au schéma. Ce découpage est le point important : une api qui migre elle-même rejoue la migration autant de fois qu'il y a de répliques, et déguise un échec de migration en crash applicatif — un conteneur qui redémarre en boucle sans jamais dire pourquoi.

Le script gère la base **déjà peuplée sans historique** (héritage du `db push`) : si une table connue répond, il déclare `0_init` appliquée (baseline) avant de dérouler la suite ; sinon il part d'une base neuve et crée tout. La distinction se lit sur le contenu réel de la base, jamais sur un drapeau.

Une suppression de modèle est le cas qui compte : `db push` la refuse (`--accept-data-loss`) et bloque le démarrage, alors qu'une migration l'exprime une fois, relue en revue, appliquée au déploiement.

Et une migration oubliée ne passe plus : les migrations jouées, le script compare la **base réelle** au schéma (`migrate diff --from-url … --exit-code`) et sort en erreur si elles diffèrent, en affichant ce qui manque. C'est la base contre le schéma, et non les migrations contre le schéma, qui demanderait une shadow database. En local, `pnpm --filter @nwm/api prisma:check` fait le contrôle **autrement** : il rejoue les migrations dans une base jetable (`nwm_shadow`, créée au besoin) et compare le résultat au schéma. Comparer la base de dev au schéma n'apprendrait rien — l'api la maintient alignée par `db push`, ce serait vert quoi qu'il arrive.

## Environnements

Ils sont **déclarés**, pas connus d'avance (`packages/core/src/domain/env.ts`, réglage global page Modules → Environnements). L'union figée `dev | preprod | prod` interdisait l'env qu'une équipe veut en plus — une recette par client, une qualif —, et elle était partout : détection sur le nom et les tags, clé de famille, suffixe de webhook, estampille des libellés.

`dev` et `prod` sont les deux bouts obligatoires ; **preprod n'a rien de spécial**, elle est proposée par défaut et se supprime. Un env porte son id (ce qui s'écrit dans le tag `env:<id>` et dans le suffixe de nom, d'où le slug borné à `[a-z0-9-]`), son libellé, sa couleur, et ce que la plateforme réservait jusque-là à la prod, coché **par env** : `monitored` (ses erreurs sont remontées) et `canonicalWebhookPath` (ses webhooks gardent le path nu, l'URL publique). Un env créé n'a rien de coché — c'est la déclaration qui lui donne un rôle, pas son nom.

Ce n'est plus une liste ordonnée mais un **arbre** : chaque env dit de QUI il dépend (`after`), si bien que deux envs peuvent repartir du même amont — la recette du client A et celle du client B partent de dev sans être l'étape l'une de l'autre. `envChainPlan` lit le chemin dans cette lignée ; entre deux branches sœurs il répond `unknown`, et on ne reproche alors aucun saut d'étape. Un amont inconnu ou circulaire est rattaché au précédent plutôt que de rendre la chaîne muette.

Les fonctions pures reçoivent les envs en paramètre (défaut : la liste par défaut) et l'API les leur passe depuis `PlatformSettingsService.declaredEnvs()` / `declaredEnvIds()` ; côté web, un contexte (`lib/envs.tsx`) sert la même liste à tous les écrans — plus aucun `['dev','preprod','prod']` en dur. Conséquence à connaître : la clé de famille se dérive du nom SANS son suffixe d'env, donc déclarer ou retirer un env change les clés des workflows qui le portent (les règles `FindingIgnore` s'apparient alors par leur ancre, pas par la clé). La colonne `envChain` reste en base, dérivée des `envs` : une installation d'avant se relit comme une chaîne linéaire.

## Plateformes

Une instance déclare ce qu'elle sert (`Instance.platform`, `n8n` par défaut). Le miroir ne nomme donc plus n8n dans ses colonnes — `Workflow.externalId`, `archivedUpstream`, `missingUpstreamAt`, `externalWorkflowId` —, parce que ce qu'elles disent vaut pour n'importe quelle plateforme d'automatisation : l'id que porte l'exemplaire là-bas, le fait qu'on l'y ait archivé, la date où elle a cessé de le connaître. `n8nEmail` / `n8nPassword`, eux, gardent leur nom : ils sont réellement propres à n8n.

`WorkflowPlatformPort` (`packages/core/src/ports/workflow-platform.port.ts`) est le dénominateur commun — lister, lire, écrire, activer, supprimer, lister les exécutions — et il ne prétend PAS unifier le contenu : `raw` reste le JSON de sa plateforme, lu par le code de sa plateforme. Un blueprint Make n'a ni `nodes` ni `connections`, et une abstraction qui ferait semblant du contraire coûterait aux contrôles n8n exactement ce qui fait leur valeur. L'implémentation n8n est une enveloppe de traduction (`N8nPlatformAdapter`) au-dessus de `N8nApiAdapter`, qui reste la voie normale pour tout ce qui est propre à n8n.

L'autre moitié du port, et la plus importante, est `capabilities()` : l'adapter **déclare** ce que sa plateforme ne sait pas faire — données d'exécution lisibles, origine du catalogue de nœuds, `pinData`, étiquetage, archivage, plafond d'appels par minute, listing des exécutions global ou par workflow. Un module interroge cette liste (`GET /instances/:id/capabilities`) et dit « je ne sais pas faire ça ici » plutôt que d'afficher un écran vide : un onglet « Champs » vide sur un scénario Make est pire qu'un onglet absent, il fait croire que le contrôle est passé. Une instance déclarée sur une plateforme qu'aucun adapter ne sert échoue FORT, plutôt que de répondre les capacités de n8n pour un compte qui n'en est pas un.

**Make** est servi par `packages/adapters/make-api` (`MakeApiAdapter`), sur l'API v2 (`https://<zone>/api/v2`, en-tête `Authorization: Token <jeton>`). Trois choses que n8n n'impose pas vivent dans `make-http.ts` : la **zone** fait partie de l'identité du compte (un jeton `eu1` refusé sur `eu2` répond « Not authorized », le même message qu'un droit manquant — d'où le message explicite de `make-errors.ts`) ; le **périmètre** est obligatoire (`GET /scenarios` exige `teamId` ou `organizationId`, d'où les colonnes `externalTeamId` / `externalOrgId`) ; et le **plafond d'appels** est imposé par l'organisation (30/min sur un plan Free, lu dans `license.apiLimit`), tenu par `RateBudget` — une fenêtre glissante par zone, puisque le plafond est partagé par tous les comptes de la même organisation. Le contenu d'un scénario n'est PAS dans le listing (`listIncludesContent: false`) : le miroir ne redemande le blueprint que des scénarios dont `changedAt` (`lastEdit`) a bougé, sans quoi une resynchro coûte un appel par scénario à chaque passe. Le pur est dans `packages/core/src/domain/make/` (traduction d'un scénario, statuts `1/2/3`, messages d'erreur) — un compte Make n'est pas une dépendance de test acceptable.

Les **boutons de l'écran** suivent la plateforme : `workflowActions()` (domaine pur `workflow-actions.ts`) rend, pour chaque geste, s'il est proposé et SINON pourquoi — et le pourquoi distingue deux choses qu'il ne faut pas confondre. `platform` : Make ne le permet pas (pas de `pinData`, pas de données d'exécution), aucun travail d'ici n'y changera rien. `not-yet` : nous ne l'avons pas porté, c'est une dette et non une limite du fournisseur. Le calcul est servi par l'API dans `Workflow.actions` (le web ne dépend pas de `@nwm/core`, et deux tables de vérité divergeraient au premier module porté), les boutons indisponibles sont masqués, et une ligne sous la barre annonce combien manquent avec la raison au survol — masquer sans le dire ferait croire que la fonction n'existe pas.

La **vue** d'un scénario est rendue par le même objet que celle d'un workflow n8n (`WorkflowViewService.makeView`, schéma par `blueprint-view.ts`) : doubler la page pour une plateforme de plus l'aurait fait diverger au premier changement. Ce qui n'existe pas chez Make y vaut zéro plutôt que d'être omis. Et surtout, `WorkflowsService.getRaw()` **REFUSE** un workflow qui n'est pas n8n : une trentaine de services lisent `raw` en le typant `N8nWorkflow` sans vérifier d'où il vient, et tombaient sur un `undefined.map` illisible. Un refus nommé se lit à l'écran ; les services qui savent gérer les deux passent par `getRawAny()`.

S'y ajoute la **conformité au schéma** (`make-schema.ts`) : Make embarque la description de ses modules DANS le blueprint (`metadata.expect` décrit le `mapper`, `metadata.parameters` les réglages), avec types, champs requis et valeurs admises — il n'y a donc pas besoin de catalogue pour juger ce qui est écrit, contrairement à ce que le doc de conception annonçait. Ce qui manque encore est ailleurs : rien ne décrit un module ABSENT du scénario, ce qui rebloquerait un assistant qui voudrait en ajouter un. Une valeur portant une expression n'est jamais jugée, les clés que Make gère lui-même (`__IMTCONN__`, `feeder`) sont écartées, et un module sans description ne produit RIEN — c'est un trou de la description, pas une faute.

Les **contrôles** aussi (`runMakeChecks`, `packages/core/src/domain/make/make-checks.ts`) : renvoi vers un module inexistant ou qui n'aura pas tourné, agrégateur sans itérateur ou rattaché à un module qui n'itère rien, If/Else sans Merge, filtres de Merge en nombre différent des branches, secret en clair, valeur d'exemple. Le parcours d'un blueprint est RÉCURSIF par nature (`blueprint.ts`) — les routes vivent dans `routes[]`, les branches dans `branches[]`, les gestionnaires dans `onerror[]` — et l'imbrication porte déjà l'atteignabilité : une route ne voit pas sa sœur, ce qui rend une référence croisée fautive sans avoir à rejouer un graphe. `CheckFinding` a quitté `domain/n8n/` : les deux plateformes produisent le MÊME objet, sinon il aurait fallu doubler la page des findings, les règles d'exclusion et la porte de l'assistant. Ce qui ne tourne pas sur Make : le schéma des nœuds (pas de catalogue) et la revue IA (son prompt est écrit pour n8n).

Les **erreurs** aussi (`ErrorWatchService.collectPlatformErrors`) : même poll par scénario, même curseur horodaté, même filtre posé avant l'appel — et le reste de la chaîne ne bouge pas, puisque les erreurs entrent dans `ExecutionError` sous la même forme et repartent dans le même événement. Le détail (message, module fautif) vient de `GET /scenarios/:id/executions/:id`, seule route Make qui le donne ; elle ne rend jamais de pile ni de données, ce qui suffit — c'est le message et le nœud qui font la signature d'un groupe. Le poll est volontairement INDÉPENDANT de celui de `performance`, qui lit pourtant les mêmes logs : un chien de garde qui s'arrêterait parce qu'un autre module a été désactivé serait pire qu'inutile, il serait trompeur. L'**import d'historique** parcourt les scénarios un par un, faute de listing global — avec deux différences avec le poll, qui se lisent dans le résultat : la profondeur dépend de ce que Make garde autant que de `days` (`oldest` dit jusqu'où on est remonté), et un scénario ÉTEINT est quand même parcouru, puisqu'un import regarde le passé, où il tournait peut-être. La **catégorisation** connaît désormais les deux vocabulaires : n8n rend des codes système (`ECONNREFUSED`), Make des noms de classe (`ConnectionError`, `DataError`) et de l'anglais courant. `RuntimeError`, `InvalidConfigurationError` et `MaxFileSizeExceededError` restent en `other` à dessein — mieux vaut « à regarder » qu'un faux tri.

La **performance** aussi (`ExecutionStatSamplerService.samplePlatformInstance`), et l'écart de forme vient d'une contrainte réelle : n8n liste les exécutions de toute l'instance d'un coup, Make ne les liste que scénario par scénario. D'où trois différences assumées — on ne poll QUE les scénarios actifs et d'env surveillé (le filtre est posé AVANT l'appel, là où n8n le pose après faute de pouvoir choisir) ; le curseur est un HORODATAGE et non un id d'exécution (`imtId` est une chaîne dont rien ne garantit l'ordre numérique, et se tromper là-dessus ferait rater des exécutions en silence) ; et la première passe pose le curseur SANS appeler, puisque interroger tout le parc pour ne rien garder brûlerait le budget de la première minute. Les bornes étant larges à dessein, une même exécution peut être revue : `skipDuplicates` s'en charge. La durée vient de Make (`PlatformExecution.durationMs`) plutôt que d'un calcul sur deux horodatages.

Le **miroir** dispatche sur `Instance.platform` (`WorkflowSyncService.syncPlatformInstance`) : n8n garde son chemin, les autres passent par le port. Le chemin commun ne redemande le contenu que si `changedAt` a bougé depuis la dernière lecture (mémoire de process, jamais une colonne : c'est une économie d'appels, pas une donnée, et un redémarrage la reperd sans dommage) — une passe en régime établi coûte alors UN appel pour tout le parc, contre trois par scénario modifié. Il n'estime pas le temps gagné (le calcul lit des nœuds n8n) et ne rattrape pas les absents à l'unité : chez Make, un scénario hors liste est à la corbeille, et l'y redemander coûterait un appel pour un 404 certain. `WorkflowSyncedEvent.raw` est `unknown` et porte `platform` : `versioning` le STOCKE sans le lire, donc un blueprint Make se sauvegarde par le même chemin qu'un workflow n8n — et se RESTAURE par le même : `restore()` écrit par `port.updateWorkflow` (chez Make `PATCH /scenarios/{id}`, blueprint sérialisé en chaîne, nom remis), ce qui rend la sauvegarde utile au-delà des 60 jours où Make garde ses anciens blueprints. Sans `confirmed=true`, à dessein : une vieille version qui ramène une app retirée de l'organisation est refusée plutôt que de l'y réinstaller en silence. Le planning vit hors du blueprint et n'est donc pas restauré — le preview le dit, avec les connexions citées par la version et plus par le scénario d'aujourd'hui (`blueprint-diff.ts`).

Le domaine suit la même ligne : `packages/core/src/domain/n8n/` porte tout ce qui lit ou écrit le CONTENU d'un workflow n8n (62 fichiers : graphe, expressions, paramètres, types de nœuds, checks), et `packages/core/src/domain/` garde ce qui parle de la plateforme À NOUS et vaudra pour Make sans une ligne de plus (30 fichiers : signature d'erreur, statistiques d'exécution, chaîne d'environnements, semver, profils de contrôle, clé de finding, famille de workflow). Le critère est TRANSITIF — un fichier qui ne compile pas sans les types n8n est rangé avec eux —, si bien que `llm-pricing.ts` ou `kuma-redundancy.ts` s'y trouvent pour un simple type emprunté ; le jour où ça gêne, c'est le type qu'on sortira, pas le fichier qu'on remontera. Rien n'est réexporté différemment : tout passe par `packages/core/src/index.ts`, donc aucun import d'`apps/` ne change.

Conception et périmètre module par module : [docs/multi-plateforme.md](docs/multi-plateforme.md).


## Catalogue des types de nœuds

Ce que n8n déclare de ses PROPRES nœuds — quels paramètres existent, de quel type, sous quelle condition, quelles valeurs sont admises. Jusque-là la plateforme n'en savait rien : `param-shape.ts` ne pouvait qu'inférer une norme des nœuds déjà présents sur l'instance (« onze nœuds Notion mettent un objet ici »), signal utile mais muet sur un type jamais employé — le cas exact d'un `add-node` proposé par l'assistant, qui écrivait alors les paramètres de mémoire.

Deux sources, deux tables, et l'instance prime à la LECTURE (`NodeCatalogService`) :

- **`NodeType`** — catalogue mutualisé, importé de [n8n-mcp](https://github.com/czlonkowski/n8n-mcp) (MIT), qui extrait et versionne ces schémas en continu. L'adapter (`packages/adapters/node-catalog`) télécharge son SQLite, n'en garde que les nœuds cœur (832 ; les 1 784 communautaires pèsent l'essentiel du fichier pour des intégrations que l'instance n'a pas) et **range tout chez nous**. C'est la raison d'être de la table et non un cache : l'amont peut disparaître, la plateforme continue de vérifier. Le cron hebdomadaire ne télécharge rien tant que le sha du blob amont n'a pas bougé.
- **`InstanceNodeType`** — ce que SERT une instance : sa version de n8n, ses nœuds communautaires installés, et — seul endroit où on l'apprend — les `typeVersion` réellement servies. Demande un compte n8n par instance (`n8nEmail` / `n8nPassword`, secrets jamais renvoyés à l'UI) : la clé API n'ouvre que `/api/v1`, alors que `/types/nodes.json` et `/types/node-versions.json` sont protégés par le **cookie de session** (`server.ts` : « Protect type files with authentication »). D'où `n8n-session.ts`, qui ouvre une vraie session et la GARDE — n8n limite les connexions à 5/min par compte, et une synchro qui se reconnecterait à chaque appel emporterait aussi les connexions de l'humain qui partage ce compte.

Le contrôle lui-même est pur (`packages/core/src/domain/node-schema.ts`) et vit HORS de `runWorkflowChecks()`, qui est sans IO : il reçoit les schémas, comme `checkParamShapes` reçoit ses références. Il sert `verifier`, l'outil `check_workflow` de l'assistant, et deux outils de plus — `describe_node_type` et `search_node_types`, sans lesquels un `add-node` d'un type absent de l'instance ne se comparait à RIEN.

Trois règles, toutes issues d'une mesure sur les 2 352 workflows publics qu'embarque l'amont — sans elles le contrôle produisait **1,52 finding par workflow**, contre 0,02 aujourd'hui :

- **Version pour version.** Le catalogue mutualisé ne décrit qu'une version par type, la plus haute, or 45 % des nœuds tournent sur une version ANTÉRIEURE dont les paramètres portaient d'autres noms (`sheetName` était une chaîne avant d'être un resourceLocator). Juger hors de sa version faisait 2 546 faux positifs à lui seul. L'instance n'y échappe PAS non plus, contrairement à ce qu'on avait d'abord posé : `/types/nodes.json` sert la description courante d'un type, pas celle qui a shippé avec la typeVersion 2 — elle dit quelles versions elle sert, jamais ce que chacune déclarait. Sur le même corpus, juger hors de sa version produit 5 « sous-clés non déclarées » et les 5 sont fausses (le Switch v2 range ses règles sous `rules`, le v3 sous `values`) : sur la seule règle qui BLOQUE une écriture, c'est cinq workflows qu'on ne pourrait plus modifier du tout. Le prix serait la couverture — 54 % des nœuds du corpus, le reste tournant sur une version que rien ne décrit —, d'où les **schémas datés** (`InstanceNodeTypeVersion`) : la plateforme demande à l'instance la description du nœud tel qu'il est ÉCRIT, par la route que l'éditeur n8n s'appelle à lui-même pour dessiner un vieux nœud (`POST /rest/node-types`, corps `{nodeInfos:[{name,version}]}`, même session cookie que `/types/*.json`). On ne demande que les couples (type, version) réellement employés par les workflows de l'instance — décrire 800 types dans toutes leurs versions ferait des milliers de lignes pour des nœuds que personne n'utilise. n8n résout le lot en `Promise.all` : un seul couple inconnu fait échouer TOUT le lot, d'où la découpe en deux à chaque échec, qui isole les fautifs en quelques appels là où un repli couple par couple ferait une requête par nœud du parc. Un couple non décrit n'est pas une panne : on retombe sur le catalogue mutualisé, et la règle ci-dessus fait taire le contrôle comme avant. La lecture va du plus précis au plus général (`schemaKey` : `type@version`, puis `type`), et le rafraîchissement suit le cron hebdomadaire — un nœud d'une version jamais vue n'est donc couvert qu'à la passe suivante.
- **Un nom, plusieurs propriétés.** Un nœud déclare souvent une `operation` PAR ressource. N'en retenir qu'une faisait refuser `download` comme « non proposée » alors qu'une autre variante l'admet : 624 faux positifs. On raisonne par nom, sur l'union des variantes applicables, et une seule qui accepte suffit à dédouaner.
- **Ce que n8n greffe hors schéma** (`pollTimes`, `descriptionType`, `requestOptions`) n'appartient à aucun nœud : 779 « paramètres inconnus » qui n'en étaient pas.

Le seul contrôle en `error` — donc bloquant à la porte DEV/PROD — est la **sous-clé de collection non déclarée**, et c'est le plus précieux : pour une `fixedCollection`, n8n confronte les sous-clés du JSON à `options[].name` (`getNodeParameters`), et une clé inconnue fait échouer l'import du workflow ENTIER (« Could not find property option », sans dire quel nœud) ou, sur les n8n plus récents où ce `throw` est devenu un `continue`, se fait jeter en silence — le workflow s'importe, l'éditeur ne dit rien, le paramètre n'existe pas. Le contrôle est RÉCURSIF parce que le cas réel vit à trois niveaux de la racine (`propertiesUi.propertyValues[].fileUrls`, où Notion déclare `fileUrl` et non `values`) : arrêté au premier niveau il ne voyait rien de ce qui compte. Le nom fautif est toujours plausible — `values`, `value`, `items` —, signature d'un JSON écrit par une IA ou par l'API là où l'éditeur aurait posé le nom déclaré. Et c'est le seul finding qui échappe à la règle « on ne compte que ce que la modification INTRODUIT » (`WRITE_REFUSING_CODES`), annoncé à l'assistant DÈS le contexte du tour — pas au moment du refus : rien de ce qu'il proposera ne pourra être appliqué tant que ce n'est pas corrigé, y compris une demande sans rapport, et l'apprendre après coup coûtait un aller-retour pour une proposition inapplicable : n8n rejette le FICHIER, pas la ligne, donc une sous-clé posée il y a trois mois dans un nœud auquel on ne touche pas fait échouer l'écriture d'aujourd'hui. La porte le dit avant le PUT, avec le nom du nœud — n8n, lui, ne le donne pas. Contournable par `force`, mais pour rien quand le contrôle a raison.

Note d'image : l'import lit un SQLite avec `node:sqlite`, d'où le passage de l'api à **node:22-alpine**. L'alternative (`better-sqlite3`) aurait mis une chaîne de compilation native dans l'image pour un fichier lu une fois par semaine.

## Règles d'architecture (OBLIGATOIRES)

1. **Hexagonal** : le domaine (`packages/core`) ne dépend d'AUCUN framework ni d'aucun système externe. Les accès externes (n8n API, GitHub, Google Drive, Anthropic, Uptime Kuma) passent par des **ports** (interfaces dans `packages/core/src/ports`) implémentés dans `packages/adapters/*`. L'API NestJS injecte les adapters via des tokens DI (`apps/api/src/infra/adapters/adapters.module.ts`).
2. **Un fichier = une responsabilité.** Jamais de fichier fourre-tout. Un service qui grossit se découpe en plusieurs services/fichiers.
3. **Modulaire & désactivable** : chaque fonctionnalité est un module NestJS autonome dans `apps/api/src/modules/<module>`. Un module :
   - expose un `manifest.ts` (`ModuleManifest` de `@nwm/core`) ;
   - est chargé dynamiquement par `modules.loader.ts` (import dynamique + try/catch : **supprimer le dossier d'un module ne casse pas le build ni le runtime**) ;
   - protège ses routes avec `@ModuleId('<id>')` + `ModuleEnabledGuard` ;
   - garde ses handlers d'événements derrière `registry.isEnabled(<id>)`.
4. **Communication inter-modules par événements uniquement** (EventEmitter2 derrière `EventBusService`). Noms et payloads typés dans `packages/core/src/events/events.ts`. Un module n'importe JAMAIS le service d'un autre module métier.
5. **Modules "core" non désactivables** : `instances`, `workflows`, `module-admin`. Tout le reste est désactivable depuis l'UI (page Modules).
6. **Refine simple-rest** : les endpoints CRUD respectent la convention `?_start&_end&_sort&_order` + header `x-total-count` (helper `apps/api/src/common/crud/paginate.ts`).

## Modules métier

| id | rôle |
|---|---|
| `versioning` | snapshot des workflows en DB + export GitHub / Google Drive. Le fichier exporté est identifié par le **externalId** (`<instance>/<nom>--<externalId>.json`, le nom n'est là que pour la lisibilité) et son emplacement est mémorisé par cible dans `WorkflowExportRef` : un renommage **déplace** le fichier (commit + suppression de l'ancien chemin sur GitHub, réécriture du même fileId sur Drive) au lieu de créer un doublon. Les fichiers hérités des renommages d'avant sont traités par `ExportCleanupService` (page Versions → menu `···` → « Nettoyer les doublons ») : il identifie chaque fichier par le externalId lu dans son nom ou, à défaut, dans son contenu, et ne supprime que ceux dont la sauvegarde à jour existe déjà. Un workflow **retiré côté n8n** — archivé nativement (`archivedUpstream`) ou supprimé (`missingUpstreamAt`), et non l'archivage doux de la plateforme, réversible d'un clic — voit son export **déplacé** dans `archived/` (`workflows/archived/…` sur GitHub, préfixe `archived__` sur Drive) par `ExportArchiveService`, à l'écoute de `instance.synced` : n8n continue de LISTER ses archivés, donc la synchro les resnapshote et l'export réécrivait leur fichier à côté des vivants, indéfiniment. Déplacé et jamais supprimé — la sauvegarde d'un workflow que n8n ne connaît plus est justement celle qui vaut le plus cher —, et le fichier ressort de `archived/` si n8n remet le workflow en service. Le rangement se décide sur l'emplacement RÉEL du fichier (`WorkflowExportRef`) et non sur une transition observée : les workflows archivés avant l'arrivée de ce rangement n'en émettent aucune, et une passe qui échoue se rejoue telle quelle — la même passe se déclenche à la main par `POST /versions/archive-sweep` (`?instanceId=` pour une seule instance), qui refuse de tourner en double comme l'export global. Les versions, elles, continuent d'être snapshotées en base (déjà masquées des vues par `workflowFilter`). Un snapshot produit par une **promotion** porte en plus son numéro (`WorkflowVersion.semver`, colonne Version de l'historique) : `Workflow.version` dit l'état courant, le snapshot dit quelle version a mis CE contenu en service |
| `verifier` | vérification structurelle (refs de nœuds, expressions, orphelins ; une ref n'est fautive que si le nœud visé n'aura PAS tourné — domaine pur `expression-reach.ts` : branche exclusive d'un IF/Switch, nœud en aval, autre trigger. Une branche sœur d'un même tronc tourne dans la même exécution et ne se signale pas) + checks de fiabilité (domaine pur `reliability-checks.ts` : HTTP sans retry/timeout, erreur avalée par `continueRegularOutput`, secret en clair dans les paramètres — chaque finding porte son correctif dans `data.suggestion`, affiché sous le message) + revue logique IA, à qui l'on dit quels nœuds ne sont atteignables que par le bouton « Execute workflow » (domaine pur `manual-branches.ts`) : une branche de mise au point écrase des données exprès, la juger comme du chemin de production produisait un avertissement à chaque passe — consigne dans le prompt ET rétrogradation déterministe en `info`. S'y ajoute la **conformité au schéma du nœud** (`node-schema.ts`, alimenté par le catalogue — cf. plus bas) : sous-clé de collection non déclarée, paramètre inconnu, valeur hors des choix, expression posée là où n8n attend une collection. S'y ajoute le **câblage des boucles** (`loop-wiring.ts`) : « Loop Over Items » range ses sorties dans l'ordre inverse de l'intuition (0 = `done`, 1 = `loop`), si bien que le corps se retrouve branché sur `done`, ou que la branche `loop` ne se referme pas sur le nœud — un seul lot traité, sur un workflow qui s'importe et paraît vert. Les deux sont en `error`, donc une proposition de l'assistant qui les INTRODUIT est refusée à la porte. S'y ajoutent les **valeurs d'exemple jamais remplacées** (`placeholder-params.ts` : `YOUR_API_KEY`, `<domaine>`, `example.com`, `changeme`) — `reliability-checks.ts` les écartait exprès de sa chasse aux secrets, si bien qu'un nœud jamais configuré ne se voyait qu'à la première exécution réelle ; le contenu d'un nœud Code est laissé à `js-checker`, qui sait en donner la ligne. Tous ces checks purs sont réunis derrière `runWorkflowChecks()` — même liste pour l'analyse et pour la relecture de l'assistant |
| `js-checker` | analyse des nœuds Code (parse acorn + heuristiques + IA). Chaque finding porte sa **position** (`data.line` / `data.snippet`, domaine pur `code-location.ts`) et son correctif (`data.suggestion`) : sans la ligne, traiter une remarque impose de rouvrir n8n et de relire le nœud entier. La revue IA doit citer le code visé (`quote`, relocalisé dans le source — introuvable ⇒ pas de ligne, jamais un numéro inventé) et se tait sur ce que n8n normalise (forme du retour d'un nœud Code) ou sur un gabarit pris pour une valeur en dur (`finding-noise.ts`, filtre déterministe : un prompt seul ne s'y tient pas). Pas de règle `console.log` : la sortie n'est visible que dans l'exécution n8n, derrière un compte admin |
| `field-checker` | échantillonne les dernières exécutions (`includeData`) pour reconstituer le **schéma réel** sorti par chaque nœud, puis confronte les champs référencés dans les expressions (`$('X').item.json.foo`, `$json.foo` résolu par le parent unique) : `field-typo` (champ très proche existant, ex. `salesFistName` → `salesFirstName`) et `field-unknown`. Domaine pur dans `execution-samples.ts` / `expression-fields.ts` / `field-check.ts` |
| `remote-schema` | « le distant a-t-il tout ce que ce workflow attend ? » : les tables Airtable, NocoDB, Notion, Google Sheets et PostgreSQL portent-elles les colonnes que ses nœuds lisent ou écrivent. Les colonnes attendues sont PURES (`remote-requirements.ts`) : mapping figé (`resourceMapper` en `defineBelow`, `fieldsUi`, propriétés Notion `Nom|type`), sélection d'une lecture (`options.fields`), clés de rapprochement — et surtout les clés posées par les nœuds **Set en amont d'une écriture en « Map Automatically »** (`upstream-keys.ts`). C'est la pratique de la maison : une seule écriture en auto-map derrière deux Set qui décrivent chacun leur comportement, plutôt que deux branches d'écriture — et elle rendait la table muette, `resource-fields.ts` classant un auto-map « sans action ». La remontée traverse ce qui laisse passer les items tels quels (IF, Switch, Filter, NoOp, Merge, Wait, Loop), fait l'UNION des Set de toutes les branches, suit `includeOtherFields` vers l'amont, et dit `partial` — jamais « rien à vérifier » — dès qu'une source n'est pas lisible dans le JSON (Set en mode JSON, nom calculé, HTTP, Code, déclencheur). Les clés connues restent certaines : un Set qui les pose les envoie. Sheets en « insérer en nouvelle colonne » (défaut n8n) n'exige rien du distant, « ignorer » rend un `warning` (la donnée se perd sans erreur). Les tables se lisent par un **workflow n8n temporaire authentifié par la credential du nœud** (`infra/n8n-probe`, extrait de `resource-discovery` qui s'en sert aussi) : la plateforme ne détient aucun secret de ces systèmes. UNE sonde par credential, quel que soit le nombre de tables — la requête voyage dans le corps de l'appel au webhook, un corps identique n'est demandé qu'une fois (Airtable rend toute la base d'un coup) —, une sonde Postgres dédiée qui interroge `information_schema.columns` par `queryReplacement`, et deux appels pour un onglet Sheets désigné par son gid (titre, puis ligne d'en-tête). Un 404 dit « table introuvable » ; tout autre refus, un NocoDB sans URL connue (`ProviderEndpoint`) ou un nœud sans credential rendent la table `unverified` avec sa raison — ni vert, ni bloquant. Codes `remote-table-missing` / `remote-column-missing` (`error`, colonne proche en suggestion), groupe « Tables distantes » du catalogue de contrôles. Bouton « Vérifier le distant » de la page workflow (lu sur l'instance du workflow, sonde conservée en cas d'échec pour être ouverte dans n8n). **À la promotion**, le même contrôle (`infra/remote-schema`, pour qu'`env-switcher` le joue sans importer le module) tourne sur le candidat DÉJÀ basculé, donc avec les ids de tables et les credentials de la cible, lus sur l'instance cible : une colonne absente est un gate bloquant contournable par `force` — elle ne se verrait sinon qu'à la première exécution réelle, en prod. `checkRemote` est opt-in côté API (chaque passe crée des sondes), coché par défaut dans la modale ; il est rejoué à chaque écriture (sous-workflow en cascade, étape de chaîne), une lecture restant en cache une minute puisque le preview se rejoue à chaque option cochée. Pas encore porté sur Make (`workflowActions`, `not-yet`). Le type des colonnes n'est pas confronté : les types n8n et ceux des providers ne se recoupent pas sans table de correspondance, et un faux positif sur une porte bloquante coûte plus cher qu'un contrôle absent |
| `tester` | tests de workflows (webhook, copie bouchonnée via pinData) + **bouchonnage guidé** (bouton « Tester sans rien envoyer ») : les nœuds qui SORTENT du système sont détectés (domaine pur `side-effect-nodes.ts` : mail, message, HTTP en écriture, opération d'écriture quel que soit le provider, appel de sous-workflow) et **pré-cochés** — un envoi réel pendant un essai ne se rattrape pas, un bouchon en trop se voit dans le résultat. Exception : un nœud dont la ressource est couverte par un mapping env n'est pas pré-coché, la bascule vaut mieux que le bouchon. Les appels de sous-workflow ont deux traitements : épinglé (rien ne part) ou **rerouté vers un workflow `[BOUCHON]`** créé au besoin et réutilisé (`stub-workflow.ts`) — l'appel part dans le vide, et son exécution n8n montre ce qui aurait été envoyé. Bouchons et copies `[TEST]` sont **étiquetés à la création** et exclus du miroir comme les bancs, sans réglage pour les lever (`tester-workflows.where.ts`) : la synchro les ramène comme n'importe quel workflow, et ils pollueraient sinon listes, couverture d'analyse, findings et versions. C'est le TAG qui les sort, pas le préfixe du nom — « [TEST] Facturation » est aussi un nom qu'un humain pose à la main ; le bouchon garde en plus son préfixe, que la réutilisation traite déjà comme son identité. S'y ajoutent les **cas de test enregistrés** : une exécution réelle jugée bonne devient la référence (entrée webhook = payload à rejouer, sortie du dernier nœud = snapshot attendu, comparaison normalisée `test-snapshot.ts` — ids/dates neutralisés). Rejouer appelle RÉELLEMENT le webhook puis relit l'exécution déclenchée (la réponse HTTP dépend du responseMode, elle ne fait pas foi). `lastStatus` alimente le gate de promotion. S'y ajoute le **banc d'essai d'un nœud** (domaine pur `node-bench.ts`) : un workflow autonome qui n'exécute QUE le nœud visé — `pinData` n'étant honoré qu'en exécution manuelle de l'éditeur, un banc piloté par l'API porte sa donnée dans de VRAIS nœuds Code, nommés comme les nœuds d'origine et chaînés en amont, faute de quoi `$('X')` ne résout pas. Sont simulés le parent d'entrée ET les nœuds cités par les expressions ; les sous-nœuds (modèle de langage, embeddings) sont recopiés et s'exécutent pour de vrai, comme le nœud testé, qui garde ses credentials. D'où l'écran d'impact avant lancement (ce qui sort du système, ce qu'il vise — `POST https://…` plutôt que « appel HTTP ») et la même porte que les propositions IA : en prod on bloque, sauf `force` coché. Les entrées sont pré-remplies depuis les dernières exécutions réelles (`collectNodeItems`). Le résultat se lit dans l'EXÉCUTION et jamais dans la réponse du webhook : le nœud porte `onError: continueRegularOutput` — sans quoi l'appel ne rendrait qu'un « Workflow execution failed » muet — et n8n range alors l'échec dans un item d'apparence ordinaire. Le banc est **gardé** (`[BANC] <workflow> · <nœud>`, tag `n8n-ops:banc-essai`, un par workflow×nœud, réécrit et non dupliqué, désactivé après l'essai) : on en a besoin quand l'essai a mal tourné. Il est exclu partout du miroir (`bench-workflows.where.ts`), **sans réglage pour le réafficher** — un archivé est un workflow qu'on a rangé, un banc est un outil |
| `env-switcher` | une bascule change les ids ET le **nom affiché** : n8n range le libellé d'une ressource dans `cachedResultName`, à côté de l'id, et un remplacement qui n'en tient pas compte donne un workflow qui tape la bonne base en en affichant une autre (domaine pur `resource-locator-labels.ts`, tronc commun `switch-resources.ts`). Le vrai titre vient du mapping (colonne `labels`, remplie par « Parcourir depuis n8n » — après coup le JSON n8n ne porte que des ids) ; inconnu, le libellé est estampillé de l'env (« CRM (prod) »), jamais laissé mensonger. Une **credential** se bascule comme une ressource — même mapping, même remise à jour du nom (`credential-labels.ts` : il vit dans `credentials[type].name`, hors des paramètres, et un id remplacé sous l'ancien nom fait s'authentifier en prod sous le compte de dev) — et se choisit dans le même drawer, servi cette fois de la récolte faite sur les workflows snapshotés (`/resource-discovery/credentials`) et non d'un workflow temporaire : l'API n8n ne liste pas les credentials, d'où l'absence d'entrée `credential` au catalogue de découverte. Pour le reste, tout part d'un seul bouton **Environnements** sur la page workflow (`env-assistant-modal.tsx`) : l'assistant demande d'abord ce qu'on veut FAIRE — rebrancher l'existant (danger : mêmes nœuds, autres données, et l'avertissement est armé quand le workflow est actif), copier vers un env, juste **déclarer** l'env (`POST /env-switcher/mark`, tag + nom, aucune donnée touchée — c'est ce qui prépare l'appariement par nom de la promotion), ou promouvoir — et grise les gestes dont les prérequis manquent (aucun mapping déclaré ⇒ rien à rebrancher, une seule instance ⇒ nulle part où promouvoir), avec le lien pour les créer. Sous le capot : bascule des ressources (Airtable, Sheets, Notion, NocoDB…) entre dev/preprod/prod via `ResourceMapping` + **promotion inter-instances** (`instance-promoter.service.ts`, page workflow → Environnements → « Promouvoir vers <env suivant> », même instance et étape suivante proposées d'emblée) : le workflow est poussé vers une autre instance n8n — **ou vers un autre env de la même instance** quand dev et prod y cohabitent sous des noms suffixés (« X - DEV » repoussé sur « X - PROD »), l'env cible étant alors obligatoire, faute de quoi le workflow s'écraserait lui-même —, ressources basculées si un env cible est choisi, correspondance **par nom** sur la cible (même nom → écrasement, sinon création inactive — pas de table de liaison à entretenir) ; le preview est obligatoire dans l'UI et crie quand la cible est active, et porte des **quality gates** : findings error et tests rouges BLOQUENT (contournable par `force`, case à cocher explicite), credentials jamais vus sur la cible (heuristique par nom, l'API n8n ne liste pas les credentials) et ressources hors mapping avertissent. Les **sous-workflows appelés** sont repointés vers leur contrepartie sur la cible, par NOM comme le reste (`sub-workflow-mapping.ts`, réécriture du seul paramètre `workflowId` par `sub-workflow-refs.ts` — nom affiché remis à jour au passage) : un id n8n ne vaut que dans son instance, et une copie qui garde celui d'origine rappelle la source, quand n8n ne refuse pas l'appel (« the sub-workflow cannot be called by this workflow »). Sans contrepartie sur la cible ⇒ gate bloquant en promotion, à moins de la **cascade** (case cochée par défaut) : les sous-workflows manquants sont promus d'abord, les plus profonds en tête, en **création seulement** — un workflow déjà présent sur la cible sous le nom attendu n'est jamais réécrit. Un sous-workflow que la plateforme n'a pas synchronisé reste bloquant : on ne sait pas le créer. Un homonyme **archivé** côté n8n (`isArchived`) n'est jamais une contrepartie valable : à nom égal l'exemplaire vivant prime, et s'il n'y a que l'archivé — cible directe ou sous-workflow appelé — la promotion bloque **sans contournement par `force`**, puisque n8n refuse toute écriture sur un archivé (« Cannot update an archived workflow ») et ne l'exécute plus ; à désarchiver ou renommer dans n8n. La duplication vers un env a son aperçu (`POST /env-switcher/duplicate/:id/preview`, noms relus de n8n : elle CRÉE sans apparier) et la même cascade (case cochée, `duplicateToEnv({ cascade })`) : un sous-workflow sans copie « - ENV » est dupliqué à son tour, une copie déjà là est réutilisée telle quelle. Elle sait aussi **bouchonner** la copie (`pinNodes`, liste empruntée au plan du module `tester`, case décochée par défaut — la copie est faite pour tourner pour de vrai une fois les ressources basculées). Les **points d'entrée** (webhook, formulaire, chat) suivent une seule règle, copie comme promotion (`webhook-paths.ts`) : une cible écrasée garde son URL — path ET `webhookId` —, un exemplaire créé reçoit un path suffixé de l'env. Le Form Trigger range son path au premier niveau jusqu'à la 2.1, dans `options.path` ensuite, et sans path son URL est `/form/<webhookId>`, un uuid que l'éditeur n8n ne laisse plus modifier ; or n8n n'enregistre une URL que par (path, méthode), l'uuid n'étant qu'une colonne. D'où la convention : un formulaire GARDE son uuid d'un env à l'autre et l'env se lit dans le Form Path — `/form/<uuid>-dev`, `/form/<uuid>-preprod`, `/form/<uuid>` nu pour l'env à URL publique (path retiré plutôt qu'égal à l'uuid). Le Webhook, lui, reçoit toujours un `webhookId` neuf, et un trigger qui ne sait pas porter de path (Chat Trigger) aussi, faute d'autre moyen de libérer l'URL. `entry-path.ts` est le seul endroit qui sache où lire et écrire ce chemin ; la détection des paths disputés propose `<uuid>-dev` à une copie qui tient encore l'uuid nu, et ne renvoie à l'humain que les triggers sans path possible. La **promotion** fait le même contrôle AVANT d'écrire (`entry-clashes.ts`, lu sur la liste des workflows de la cible que l'aperçu charge déjà) : une URL que la cible va servir et qu'un autre workflow de l'instance tient déjà — la dev restée sur l'uuid nu, promue tout droit vers la prod — est annoncée, et son détenteur passé sur le path suffixé de SON env avant l'écriture de la cible (`moveClashing`, oui par défaut ; un échec arrête la promotion avant d'avoir rien écrit). Refusé, un détenteur ACTIF bloque, contournable par `force` ; un inactif ne sert rien aujourd'hui et n'est qu'annoncé. Sur un n8n à **versions**, publier un workflow exige que chaque sous-workflow qu'il appelle soit publié (`activeVersionId`, contrôle `validateSubWorkflowReferences` de n8n, sur les seuls `executeWorkflow` actifs d'id fixe) — or la cascade crée ses appelés en brouillon, si bien que le workflow promu ne s'activait plus, et qu'une cible déjà publiée refusait jusqu'à l'écriture, qui la republie. La promotion publie donc les appelés en brouillon AVANT d'écrire la cible, les plus profonds d'abord (`callee-publication.ts`, relus dans n8n un par un : la cascade vient peut-être d'en créer), mais seulement ceux qui ne démarrent RIEN seuls — déclencheur d'appel et bouton manuel ; un webhook ou une planification les mettrait en route, et ceux-là restent à l'humain avec la raison, comme leurs appelants (`publishCallees`, oui par défaut). Un refus de n8n n'arrête pas la promotion : il est rendu, et l'activation le redira. La cible elle-même n'est jamais publiée d'office : promouvoir ne déploie pas — **sauf option « Publier comme la source »** (`publishLikeSource`, décochée par défaut). Cochée, une fois TOUT écrit (étapes de chaîne comprises, jamais entre deux : une pause ne laisse qu'une publication à finir, pas une promotion à moitié écrite), chaque exemplaire de la cible est publié si son homologue l'est dans la source — le workflow promu et, en récursif, ses appelés, quel que soit leur déclencheur : c'est l'état de la source qui décide. L'ordre est celui des appels, feuilles d'abord (domaine pur `publication-chain.ts`, appariement source/cible par le NŒUD qui appelle — `pairCallees` —, la promotion ne réécrivant que l'id) ; un brouillon en source reste en brouillon. Au premier refus de n8n (ou exemplaire verrouillé) la chaîne se met en **pause persistée** (`PromotionPublishRun`) plutôt que de continuer : ses appelants seraient refusés à leur tour, et le message utile noyé dans leurs échecs. Le refus s'affiche tout de suite, et la chaîne se reprend, se passe (étape par étape) ou s'abandonne depuis un bandeau de la fiche, source comme cible (`/env-switcher/publish-runs`). Chaque étape relit n8n avant de publier : une reprise ne republie pas ce qu'un humain a publié entre-temps. Au rejeu d'une procédure, une pause met l'étape en attente d'un humain. La promotion, elle, ne transporte JAMAIS le `pinData` de la source : un bouchon d'essai qui atterrit sur la cible y ferait servir de la donnée factice. Elle ne transporte pas non plus l'ÉCRITURE d'un sélecteur de ressource : un id tapé en dev (`mode: id`, `=appX` sans gabarit) qui vise la même ressource que le choix de liste de la cible reprend l'écriture de la cible, nom affiché compris (`resource-locator-form.ts`), et le diff comme l'empreinte d'écart comparent les sélecteurs sous leur forme canonique — sinon un simple changement de forme s'affichait en « 3 modifiés » et poussait l'IA à proposer une majeure. L'IA, elle, ne propose jamais plus d'un cran au-dessus de la règle déterministe (`capAiBump`). L'appliquer resynchronise la cible → snapshot `versioning`. **La promotion pose la version** (`Workflow.version`, semver) : c'est elle qui fait la release, éditer en dev ne bouge rien. Le numéro suivant part de la PLUS HAUTE du workflow métier, tous envs confondus (domaine pur `semver.ts`) — repartir de la seule source rejouerait un numéro déjà servi ailleurs — et il est posé **sur tous les exemplaires que la promotion touche**, source comprise : même contenu, même numéro, et l'écart entre deux envs se lit d'un coup d'œil. Encore faut-il qu'il y ait quelque chose à publier : un numéro identifie un CONTENU et non un geste, donc une source qui n'a pas bougé depuis sa mise en service voit son numéro **repris tel quel** au lieu d'être incrémenté (`ReleaseStateService`, clé de contenu `workflow-release-key.ts`). Sans cette reprise, promouvoir dev → preprod aujourd'hui puis preprod → prod demain donnait deux numéros pour un même workflow, et le second ne décrivait aucune modification. La question se tranche sur la LIGNÉE de la source — le dernier snapshot qui porte un `semver` EST le contenu mis en service — et jamais sur le diff avec la cible, qui ne parle que de la cible. La clé ignore le marqueur de version dans le nom (la promotion renomme elle-même l'exemplaire qu'elle publie, qui paraîtrait sale dès la synchro suivante) et le `pinData` (jamais transporté). Le numéro que l'équipe tient dans le **nom** (« Facturation (1.2.1) », domaine pur `workflow-version-name.ts`) est reconnu : il amorce la colonne tant qu'elle est vide — sinon la plateforme proposait 1.0.0 à côté d'un 1.2.1 —, et la promotion le **reporte dans le nom**, côté n8n, sur la source comme sur la cible : la colonne ne se voit que dans la plateforme, et deux numéros pour un même workflow ne valent pas mieux qu'aucun. Un nom qui n'en porte pas n'en reçoit pas. Le sort de ce renommage est RENDU avec le résultat de la promotion (`PromoteRename` : renommé, déjà à ce numéro, sans marqueur, ou refusé par n8n) et dit à l'écran : non bloquant ne veut pas dire muet, et l'échec ne vivait jusque-là que dans un `warn` des logs du conteneur — la plateforme annonçait « posé en 1.3.0 » à côté d'un n8n resté en « (1.2.2) ». C'est pour la même raison que ce numéro sort de la **clé de famille** (`workflow-family.ts`) : il BOUGE, et le garder faisait d'une montée de version un changement d'identité — historique perdu, frères introuvables, et une promotion qui crée un second exemplaire à côté de la prod vivante au lieu de l'écraser. L'appariement par nom, cible directe comme sous-workflow appelé, cherche donc le nom exact d'abord, puis le nom sans son numéro à env égal. Le digit est **proposé** au moment de la promotion à partir du diff (`version-bump.ts` : nœud retiré ou déclencheur touché ⇒ majeure, nœud ajouté ⇒ mineure, réglage ⇒ corrective), affiné par l'IA quand elle est configurée et **jamais dépendant d'elle** — la règle déterministe est à la fois la proposition par défaut et le repli, le dernier mot restant à l'humain. Une cible qui porte une version PLUS HAUTE que la source est un gate bloquant : elle a reçu quelque chose que la source n'a pas, et la promotion s'apprêtait à l'écraser — c'est la seule chose que le numéro sache dire, et elle vaut le détour. Le rangement suit la **chaîne d'environnements** déclarée (`env-chain.ts`, cf. « Environnements » plus bas : chaque env dit de QUI il dépend, un env non déclaré ne compte jamais comme étape sautée) : promouvoir dev → prod propose d'abord de **passer par** preprod (`throughChain`, coché par défaut — une promotion par étape, dans l'ordre) plutôt que de l'ignorer. Sauter reste possible en mode `warn`, sur une case `confirmSkip` distincte de `force` : confondre les deux ferait passer un saut d'étape à qui voulait seulement forcer un test rouge. En mode `block` rien ne l'ouvre, et le mode vaut **aussi pour les écritures hors promotion** (`EnvChainGuardService` : édition IA, restauration d'une version, renommage sûr, rebranchement de ressources) — une chaîne qu'on ne ferait respecter qu'à la promotion laisserait ouverte la porte par laquelle passent justement les corrections faites dans l'urgence |

TOUTES instances confondues, contrairement au corpus d'instance qui, lui, ne franchit pas la frontière (une forme de paramètre et un id de credential ne valent que chez eux, un MONTAGE voyage — et le workflow qu'on vient promouvoir n'a justement rien à copier chez lui). Sans ça l'assistant écrivait du n8n générique dans une maison qui a ses habitudes, alors que la réponse était déjà écrite dans le workflow d'à côté : le catalogue dit ce que n8n PERMET, le parc ce que la maison FAIT. S'y ajoute la **documentation des systèmes tiers** (`search_docs` / `read_docs`, port `DocsPort`, adapter Context7) : le catalogue décrit le NŒUD, le parc le MONTAGE, et ni l'un ni l'autre ne dit le nom exact d'une mutation GraphQL, d'un champ de body ou d'une valeur admise par l'API visée. C'est le seul trou qu'aucun contrôle d'ici ne voyait — un `httpRequest` impeccable côté n8n (graphe valide, schéma du nœud respecté) peut viser un endpoint qui n'existe pas, et l'erreur n'arrive qu'à la première exécution réelle, contre le serveur du tiers. Rien n'est rangé chez nous, contrairement au catalogue de nœuds : une doc d'API PÉRIME, et la garder ferait vieillir la réponse au lieu de la rafraîchir — source muette ⇒ le prompt impose de le DIRE (« je n'ai pas la doc de X pour Y ») plutôt que d'écrire un nom plausible. Clé `CONTEXT7_API_KEY` facultative : sans elle l'amont répond, plafonné par IP. Les paramètres rendus sont ceux que n8n exécute (`activeParameters`) et passent par `redactSecrets` (`secret-patterns.ts`, définition partagée avec `reliability-checks`) — un exemple est un montage, pas un trousseau. Archivés, supprimés dans n8n, bancs et bouchons en sont écartés SANS regarder le réglage d'affichage : proposer de reproduire ce qu'on a rangé n'a pas de sens. Deux exemples au plus par workflow et dédoublonnage sur les paramètres, sinon un seul auteur prolixe passe pour la convention de la maison. Un **JSON n8n collé** dans la demande est traité comme la BASE choisie et non comme une illustration (domaine pur `pasted-workflow.ts`, qui le reconnaît et rappelle au modèle chaque nœud et chaque arête à conserver) : le modèle le lisait comme une description et reconstruisait à sa façon, un IF ou une boucle en moins. Les **prompts des nœuds IA** échappent désormais à l'élagage des exemples — la plus grosse clé partait d'abord, donc systématiquement le prompt, alors que c'est la seule chose qu'on vienne chercher sur ces nœuds-là : il est coupé, jamais retiré, et le prompt décrit la façon de la maison de les écrire (rôle et cible, interdits listés, format de sortie imposé, données injectées par `JSON.stringify`, contraintes chiffrées, auto-contrôle final). Le prompt porte par ailleurs les **pratiques de construction** de l'équipe — NoOp « Start » derrière plusieurs déclencheurs, jalon nommé devant un embranchement, Set qui rapatrie le json d'un nœud d'amont, découpage en sous-workflow ou webhook sécurisé — qu'aucun exemple générique n'aurait données. Ce que la boucle a fait est repris sous la réponse : une réponse qui a relu trois nœuds ne doit pas ressembler à une réponse de mémoire. Le brouillon passé à `check_workflow` est **retenu** et sert de proposition quand la réponse finale n'en porte aucune : le modèle sérialise ses opérations deux fois — une fois pour l'outil, une fois dans son enveloppe JSON — et perdre la seconde (réponse rendue en prose, ou enveloppe tronquée par la taille du brouillon) suffisait à tout perdre, le message invitant alors à « valider le diff » qui ne s'affichait nulle part et le tour suivant recommençant à l'identique. Seul un brouillon que le contrôle a déclaré propre est repris — celui qu'il a recalé, le modèle avait ses raisons de l'abandonner — et rien n'est écrit pour autant : une proposition se relit avant de partir. L'IA peut proposer une modification sous forme d'**opérations d'édition** (`packages/core/src/domain/workflow-edit.ts`) — dont le patch de paramètres fusionne en PROFONDEUR et la suppression d'une clé a son opération dédiée (`remove-node-parameter`, qui marque au passage la colonne `removed` dans le `schema` d'un resourceMapper — sans ce drapeau, le « Refresh » de l'éditeur n8n ramène la colonne qu'on venait d'enlever, avec toutes les autres) : renvoyer le bloc parent pour en retirer une sous-clé imposait à l'assistant de recopier ce qu'il ne connaît pas, et un `schema` de resourceMapper de 800 champs repartait amputé dans n8n, où le nœud redemandait alors toute sa configuration. Un nœud qui perd un bloc entier est dit en orange dans la revue et rendu à l'assistant par `check_workflow` : le cap de la liste d'impacts le reléguait derrière un « … et 803 autres champs modifiés » ; elles sont appliquées à une copie, confrontées à l'original (`workflow-diff.ts`) et **revues en diff** avant tout PUT vers n8n. La proposition passe une **porte** (domaine pur `proposal-gate.ts`), qui rejoue les mêmes contrôles que l'outil `check_workflow` — structure, forme des paramètres apprise de l'instance, ET schéma des nœuds : sans ce dernier, la porte ignorait ce que n8n déclare de ses propres nœuds, l'assistant voyait le problème et l'application partait quand même. On ne compte que les findings que la modification INTRODUIT — un workflow déjà rouge bloquerait sinon tout ce qu'on lui fait — et une `error` introduite arrête l'application **dans tous les environnements**, contournable par la seule case `force` cochée par un humain. C'est le socle : le refus ne dépendait avant que de la prod (env déduit par `detectWorkflowEnv`, un workflow sans env déclaré mais ACTIF étant traité comme de la prod), et en dev tout passait — or le workflow de dev est celui qu'on promeut ensuite, si bien que ce qui casse s'y voyait sans jamais rien arrêter. L'env ne décide plus que de la formulation du refus. **Et la proposition ne va pas à l'écran sans avoir passé cette porte** : refusée, elle repart au modèle DANS le même tour, avec le motif, deux passes au plus (`draft-repair.service.ts`, texte pur `draft-repair.ts`) — l'assistant a bien `check_workflow`, mais rien ne l'oblige à s'en servir et ce qu'il RECOPIE dans sa réponse n'est pas forcément ce qu'il a vérifié, si bien que le refus se découvrait à l'écran sur un diff inapplicable, un tour perdu et une relance à écrire à la main. La correction remplace aussi l'explication du tour, qui décrivait la version refusée ; le modèle qui ne sait pas corriger renvoie `proposal: null` et dit ce qui lui manque, plutôt qu'un diff dont on sait qu'il ne sera pas écrit. Un refus qui survit aux deux passes est rendu tel quel : l'humain saura reformuler là où le modèle tourne en rond. Un échec d'appel IA et une proposition illisible (JSON tronqué d'une grosse modif) restent DANS la conversation : en 500 ou en silence, la demande semblait s'être perdue toute seule. La revue a deux onglets sur le MÊME changement : « Ce que ça change » d'abord — une phrase par effet, calculée sans IA (domaine pur `change-impact.ts` : cron traduit en clair, désactivation, credential, câblage lu comme « X n'alimente plus Y »), les effets qui débordent du nœud en orange — puis « Diff JSON » qui le prouve. Un diff brut montre quels caractères bougent, pas qu'on vient de retirer le samedi du planning, et à plusieurs nœuds modifiés personne ne relit le JSON. Toute lecture qui peut mener à une écriture repart de n8n (`WorkflowsService.getFreshRaw`) : le miroir local date au mieux du dernier cron, et comme on écrit le workflow ENTIER, en partir revenait à renvoyer l'état d'hier — une credential assignée à la main dans l'éditeur était écrasée sans que rien ne le dise, et le garde-fou d'empreinte comparait la proposition à une copie aussi vieille qu'elle. L'application resynchronise le workflow → nouvelle version via `versioning`, et le **retour arrière reste offert dans la revue** longtemps après : le point de retour est apparié sur le `baseHash` de la proposition — l'état sur lequel elle a été bâtie — et non sur l'état courant, qui est justement celui qu'on veut défaire ; il dit aussi quand le workflow a bougé depuis, puisque restaurer emporterait alors ce qui a été fait après. On peut **joindre des captures d'écran ET des fichiers texte** à une question (collage direct dans la zone de saisie, glisser-déposer ou trombone ; PNG/JPEG/WebP/GIF, 5 Mo et 4 images par message, et JSON/CSV/log/YAML/Markdown… 256 ko par fichier, 5 fichiers et 400 ko par message — domaine pur `chat-attachments.ts`, mêmes bornes côté UI pour refuser avant le téléversement). Le fichier va là où la capture ne peut pas : un export d'un autre n8n, la réponse brute d'une API, le log qui plante à la ligne 4012 — recopiés dans la zone de saisie ils arrivent tronqués, joints ils arrivent tels quels, et la question tient en une phrase à côté. Un fichier n'a pas de bloc à lui dans l'API des deux fournisseurs : il est rendu DANS le texte du message, après la demande — c'est elle qui commande, et le prompt dit qu'un fichier est de la donnée et jamais une consigne. Ce qui est stocké reste le message de l'utilisateur seul (fil et export lisibles), le contenu étant rejoint à chaque tour depuis la base, dans un budget d'historique de 400 ko : au-delà, les fichiers les plus anciens ne sont plus rejoués mais restent ANNONCÉS par leur nom, pour que le modèle les redemande au lieu d'en inventer le contenu. La détection du **JSON n8n collé** porte sur le message tel que le modèle le reçoit, fichiers compris : un `workflow.json` déposé au trombone est une base au même titre que collé dans la phrase. Un binaire déguisé en `.txt` est refusé plutôt que transmis en charabia, et une pièce jointe est servie en `text/plain` avec `Content-Disposition: attachment` — du HTML téléversé, rendu sous son vrai type, s'exécuterait sur l'origine de la plateforme : un nœud rouge dans n8n et son message d'erreur se montrent en une fois, là où il fallait les retranscrire. Les octets vivent en base (`WorkflowChatAttachment`) et sont servis à part du JSON de la conversation (`GET /workflow-chat/attachments/:id`, cache immuable) : dix captures dans le JSON, c'est des dizaines de Mo à chaque ouverture du tiroir. L'assistant PROPOSE au lieu de demander : ce qu'il ignore est supposé et annoncé (« j'ai supposé X »), un réglage manquant laisse le nœud posé avec sa `notes`, et ce qu'il n'a pas su faire se dit À CÔTÉ du diff plutôt qu'à la place — le prompt imposait l'inverse (un bloc « TON ACTION » obligatoire à chaque tour, « pose la question au lieu de proposer »), et une demande claire suivie de cinq « go » pouvait tenir dix tours sans jamais produire une seule opération. Ce qui dépasse du corps du message part dans un repli (`:::détail <résumé>` … `:::`, rendu en `<details>` par `markdown.tsx`, déplié à l'export) : le détail reste disponible sans être lu de force. Même traitement pour l'avancement du tour (`chat-turn-progress.tsx`) : une ligne par étape DISTINCTE avec son compteur (« Vérification du brouillon ×6 ») et les cinq dernières seulement — une trentaine de lignes dont la moitié répétées ne se lisent pas, elles se sautent. Le prompt dit quoi en faire — le workflow qui fait foi reste le contexte JSON, l'image apporte ce qu'il n'a pas (message d'erreur, valeur reçue) et un nom de nœud lu dessus mais absent du contexte se demande au lieu de s'inventer. Seules les 4 dernières images de l'historique sont rejouées au modèle, sinon chaque tour repaie toutes les captures de la conversation. Une conversation s'**exporte en Markdown** (bouton « Exporter » du tiroir : cette conversation, ou toutes celles du workflow — domaine pur `chat-export.ts`, résumé et sort de chaque proposition compris) : le raisonnement qui a mené à une modification appliquée se colle dans un ticket et se relit des mois plus tard, quand la conversation aura disparu avec le workflow. Un tour en cours s'**arrête** (bouton « Arrêter » ou touche Échap — écoutée en capture sur le document, propagation coupée, pour que le tiroir ne se ferme pas au lieu d'arrêter, `POST /workflow-chat/sessions/:id/cancel` → `AbortSignal` porté jusqu'à l'appel Anthropic et relu entre chaque aller-retour d'outil) : la demande est alors DÉFAITE — message supprimé, captures comprises — et rendue à la saisie, puisqu'on n'arrête que pour reformuler. Le registre est en mémoire et par process, comme l'avancement : un tour introuvable répond `stopped: false` et ira au bout plutôt que de faire croire à un arrêt. La saisie **complète la frappe** (fin de phrase en gris, `Tab` pour l'accepter — domaine pur `chat-completion.ts`, recopié côté navigateur qui ne dépend pas de `@nwm/core`) : demandes déjà écrites sur ce workflow, catalogue de demandes courantes et noms de ses nœuds, servis en un appel à l'ouverture (`GET .../completions`) — aucune IA dans la boucle, une suggestion qui se paie une seconde d'attente arrive après le mot suivant. Sur un **scénario Make**, le tour est confié à `MakeChatTurnService` dès que le workflow y est servi — session, historique, pièces jointes, arrêt et enregistrement restent communs, tout ce qui LIT le contenu est à part. L'assistant n'y fait que RETOUCHER des modules existants (`blueprint-edit.ts` : mapper et parameters fusionnés en profondeur, filtre, nom, suppression) : ajouter un module demanderait sa description, que Make n'embarque que pour les modules déjà présents, et l'écrire de mémoire dans le scénario d'un client est exactement ce que la porte doit empêcher. Les clés `__IMT…__` (connexion, webhook) sont refusées — un id propre au compte — et une valeur « [secret masqué …] » recopiée aussi, sans quoi le masque partirait dans Make à la place du secret. Même table de propositions, même revue (le diff Make est rendu sous la forme de celui de n8n, `blueprint-review-diff.ts`, apparié par id donc stable au renommage), même RÈGLE de porte (`evaluateMakeProposalGate` appelle `evaluateProposalGate` avec les contrôles Make), même correction dans le tour (deux passes), même écriture gardée — relecture de Make, empreinte de départ, point de retour — mais par le port Make. Les cinq outils qui ne lisent jamais le workflow (mémoire, conversations, doc des tiers) vivent dans `chat-shared-tools.ts`, communs aux deux tours. Porte aussi le pont **erreur → correctif IA** (`error-fix.service.ts`, bouton « Proposer un correctif (IA) » sur un problème de la page `/errors`) : le groupe d'erreurs devient une conversation pré-alimentée (nœud fautif, pattern, dernières occurrences) et l'IA répond par une proposition ordinaire — ou par un diagnostic SANS proposition quand le vrai correctif est hors du workflow (credential expiré, quota). Le groupe est lu directement en base, pas d'import inter-modules |

## Ajouter un module

1. Créer `apps/api/src/modules/<id>/` avec `manifest.ts`, `<id>.module.ts`, `<id>.controller.ts`, `<id>.service.ts`.
2. Déclarer le chemin dans `apps/api/src/infra/modules-registry/modules.config.ts`.
3. Ajouter les événements dans `packages/core/src/events/events.ts` si besoin.
4. Ajouter la/les resources Refine côté web si le module expose du CRUD.

## Conventions

- Docs en français, code + identifiants en anglais.
- Pas de `any` sauf frontière JSON n8n (typée `N8nWorkflow` au plus tôt).
- Erreurs HTTP via exceptions Nest standard. Filtre global `AllExceptionsFilter` : toute 5xx est journalisée (méthode + URL + cause + stack) et, si `DEBUG_ERRORS=1` (posé en dev par `docker-compose.override.yml`), la cause réelle est renvoyée dans le corps de la réponse — l'UI l'affiche telle quelle. Un 500 dont le corps n'est PAS du JSON vient du proxy Next : c'est l'API qui est injoignable (redémarrage), pas le code métier. Les erreurs Prisma sont traduites avant ce filtre (`prisma-error.mapper.ts`) : requête invalide (`_sort` inconnu) → 400, P2025 → 404, P2002 → 409 ; le détail complet reste dans les logs. Un refus d'un système tiers ne doit pas passer pour un plantage : les appels au port Uptime Kuma passent par `callKuma()` → 502 avec message lisible (`kuma-errors.ts`). De même, un 401/403 de n8n (clé API révoquée, compte refusé) ressort en 502 qui dit quoi reprendre (`n8n-error.mapper.ts`) et n'est **pas** remonté à Sentry : c'est un réglage à corriger, et chaque clic sur « Synchroniser » ouvrait un événement de plus.
- **Remontée des erreurs** (Sentry ou **GlitchTip**, qui parle le même protocole — cf. [docs/sentry.md](docs/sentry.md)) : optionnelle, et **rien n'est initialisé sans DSN**. Ce n'est pas un port hexagonal — Sentry ne rend aucun service au domaine, il observe le process : il vit dans `infra/sentry/`, s'installe en tête de `main.ts` avant `loadFeatureModules` (sinon un module qui casse au chargement ne remonte nulle part), et la capture se fait au point unique où passent déjà les erreurs HTTP, `AllExceptionsFilter`. Seuls les **5xx** partent : un 404 ou un 409 est une réponse, pas une panne. Les événements passent par `redactSecrets` — le même masquage que les logs à l'écran — et ni corps de requête, ni cookie, ni IP n'est joint. Côté front, un fichier de config par runtime Next à la racine du projet (navigateur, serveur, middleware) : `NEXT_PUBLIC_SENTRY_DSN` est **inliné au build** comme `NEXT_PUBLIC_API_URL`, il se passe donc en build arg. Traces de performance et rejeu de session à **zéro** par défaut : GlitchTip ne les stocke pas, et le rejeu enverrait le contenu des écrans — dont les workflows d'un client — à un tiers.
- **Verrou d'un exemplaire** (`WorkflowLock`, menu « ⋯ » de la fiche → Verrouiller) : plus AUCUNE écriture de la plateforme vers cet exemplaire — promotion qui l'écrase (étapes de chaîne comprises, vérifiées toutes AVANT la première écriture), déplacement d'une URL qu'il tient, édition IA (n8n et Make, sous-workflows visés compris), restauration, renommage sûr, stickies, rebranchement, déclaration d'env, correction de path, organizer, publication, archivage, suppression d'un reste du chat — sans un forçage qui le NOMME et le justifie. La portée est l'exemplaire (son id), jamais la famille ni l'env : une promotion qui CRÉE n'est pas concernée, et la source d'une promotion peut être verrouillée — son nom seul n'est alors pas renuméroté (`PromoteRename.status: 'locked'`), comme un appelé verrouillé n'est pas publié d'office. Un seul garde, `WorkflowLockService.assertWritable` (`infra/workflow-lock/`, global), appelé AVANT la première écriture de chaque geste : un refus à mi-chemin laisserait un geste à moitié fait. Le forçage voyage dans deux en-têtes (`x-lock-override` : ids levés, `x-lock-override-reason` : raison encodée, 5 caractères au moins), lus par un middleware dans un `AsyncLocalStorage` (`lock-context.ts`) plutôt que dans le corps de vingt routes : c'est `apiRequest` qui, sur un 423 `workflow-locked`, ouvre la modale (`lib/workflow-lock/`) puis REJOUE l'appel, sans qu'aucun écran n'ait à connaître le verrou. Un forçage ne lève que les exemplaires qu'il nomme, vaut pour CETTE requête seulement (le verrou reste en place) et se journalise une fois par geste (`WorkflowLockOverride` : qui, quand, quelle route, pourquoi — visible au clic sur l'étiquette « verrouillé »). C'est une case distincte de `force` et de `confirmSkip` : forcer un test rouge ne doit jamais lever un verrou. Les procédures et les actions groupées le lisent dans la readiness (`locked`, « à décider ») : un rejeu s'arrête en attente d'un humain, et le forçage n'est ni capté ni rejoué, puisqu'il ne vit que dans les en-têtes. Hors requête (cron, événement), rien n'est levé. Une édition faite directement dans n8n n'est ni bloquée ni détectée.
- Workflows archivés (tag `archived`, préfixe `[ARCHIVED]`, ou archivage natif n8n stocké dans la colonne **`archivedUpstream`** — et non lu du JSON : un `NOT` sur un chemin JSON absent vaut NULL, donc écarte la ligne au lieu de la garder) : **exclus partout par défaut** — listes, couverture d'analyse (donc jamais analysés), findings, versions, ressources externes, monitoring, découverte. Filtre centralisé : `PlatformSettingsService.workflowFilter()` (`apps/api/src/infra/settings/`, module global) à fusionner dans le `where` Prisma. Réglage `includeArchived` (`GET/PUT /settings/platform`, page Modules → Réglages généraux). Exception : la carte des workflows charge les archivés pour résoudre les appels qui les visent et les masque via son propre switch, initialisé sur ce réglage. Même traitement pour les workflows **supprimés dans n8n** : la resynchro les redemande à l'unité, un 404 les estampille `missingUpstreamAt` (`missing-workflows.where.ts`, réglage `includeMissing`) — rien n'est effacé, versions et historique d'erreurs restent consultables.
- Le miroir local se resynchronise **tout seul toutes les heures** (`workflow-sync.cron.ts`), instance par instance : sans cela il ne bougeait qu'au clic sur « Synchroniser », et la liste montrait l'état de n8n d'il y a trois semaines — un workflow archivé entre-temps s'y affichait encore comme un workflow ordinaire.
- La page **Versions** a les mêmes deux vues (`GET /versions/families`, `version-families.service.ts`), à trois niveaux : le workflow métier, ses environnements, et sous chacun son historique de versions. La question posée à cette page compare les envs (« qu'est-ce que la prod a de moins que la dev ? ») ; la vue par exemplaire les posait à deux endroits de la liste. Le repliage de l'historique reste demandé à l'ouverture, jamais pour toute la page.
- La page Workflows a deux vues : une ligne par workflow n8n, ou **groupée par workflow métier** (`GET /workflows/families`) — « X - DEV » et « X - PROD » font une ligne, dépliable sur ses environnements. La clé de regroupement est le nom débarrassé de son suffixe d'env et de son préfixe d'archivage (domaine pur `workflow-family.ts`) ; le groupement se fait côté API, sinon une famille à cheval sur deux pages serait coupée en deux. La même famille sert de **sélecteur d'env sur la page d'un workflow** (`GET /workflows/:id/siblings`, ligne « Même workflow en : DEV · PREPROD · PROD ») : on passe de la version dev à la version prod en un clic au lieu de retourner chercher le nom dans la liste ; l'instance est affichée quand le frère vit ailleurs, puisqu'un même workflow métier peut être promu sur une autre instance. Les **actions groupées** (cases à cocher, `bulk-actions.tsx` : resynchroniser, analyser, archiver, désarchiver — les appels des boutons de ligne, rejoués 4 de front) portent sur les workflows n8n dans les DEUX vues, la vue groupée cochant les membres d'une famille et jamais la famille : archiver « X » d'un clic emporterait la prod avec le dev. Une ligne sur laquelle le geste n'a pas de sens (déjà archivée, absente de n8n) est annoncée puis ignorée, jamais mise en échec — un lot normal passerait sinon pour un lot cassé. La vue groupée coche AUSSI les familles, mais pour les seuls **gestes d'environnement** (`bulk-env/` : promouvoir, dupliquer vers un env, déclarer l'env) — eux ne portent pas sur un exemplaire : on dit une fois « de DEV vers PROD » et chaque famille y trouve son exemplaire de départ et sa cible (domaine pur `bulk-env-plan.ts`, servi par `POST /env-switcher/bulk/plan` qui ne lit que la base). La cible d'une promotion est l'instance où vit déjà l'env cible, sinon une instance de repli choisie pour le lot, par défaut celle de la source ; une famille sans exemplaire utilisable, avec deux exemplaires du même env, ou dont la copie existe déjà est annoncée et ignorée. Chaque famille est ensuite prévisualisée par la route de SON geste (aucune route « de masse » : un lot porte exactement les gardes d'un workflow seul), et la preview dit ce qu'il reste à un humain (`readiness`, domaine pur `env-action-readiness.ts`) : `ready`, `decide` — diff à relire sur une cible écrasée, cible active, gates contournables par `force`, saut d'étape à confirmer, ressources sans mapping d'une copie — ou `blocked`, que rien ne lève (homonyme archivé, chaîne en mode `block`, copie déjà présente). La revue applique d'un clic ce qui est prêt et déplie le reste sur place, `force` et `confirmSkip` restant deux cases distinctes ; « Valider les N diffs relus » ne vaut que pour les lignes dont le diff est la seule décision. Les écritures partent UNE PAR UNE : deux familles qui appellent le même sous-workflow manquant le créeraient chacune en cascade si elles partaient ensemble, alors qu'en série la seconde le retrouve sur la cible par son nom.
- La page Workflows a une **disposition mobile** (sous le breakpoint `md`, 768 px — `Grid.useBreakpoint`) : les tableaux laissent place à des lignes repliées (nom + badges d'env) qui se déplient au tap, une seule à la fois (`app/workflows/mobile/`). Même requête, mêmes filtres, même sélection que le desktop (`use-workflow-list.ts`) : seul le rendu change. Pas de case à cocher visible : l'**appui long** ouvre le mode sélection (`use-long-press`), où le tap coche au lieu de déplier, et la barre d'actions groupées reste collée en haut ; dans la vue groupée, l'appui long sur un workflow métier le coche pour les gestes d'env, sur un exemplaire pour les actions groupées — les deux sélections du desktop. Les gestes sont décidés par une fonction pure (`mobile-gestures.ts`). Les filtres passent dans un tiroir bas (bouton « Filtres », badge du nombre posé — `activeFilterCount`), la recherche reste visible ; les contrôles sont les mêmes qu'en desktop (`workflow-filter-controls.tsx`, `block` pour l'empilement).
- **Écart avec la prod** (colonne « Écart prod » des deux vues, filtre « Écart avec la prod » : `?divergence=<env>` = ses exemplaires à déployer, `diverged`, `behind`) : chaque exemplaire est comparé à la prod de son workflow métier sur une empreinte sha1 (`deployKey`, domaine pur `deploy-key.ts`) de ce qu'une promotion TRANSPORTE. Un sha1 du JSON brut dirait « différent » par construction : on y neutralise ce que la promotion bascule ou préserve d'elle-même — ids des ressources mappées ramenés à leur entrée de mapping, sous-workflows et workflow d'erreur ramenés au nom métier de l'appelé, path et `webhookId` des points d'entrée, nom, libellés affichés, `pinData`, ids et positions de nœuds. Une ressource NON mappée qui diffère reste un écart : la promotion l'écraserait. Le sens (`ahead` = à déployer, `behind` = la prod a bougé en dernier, un correctif à reporter) vient des dates de modification n8n — le contenu dit qu'ils diffèrent, pas lequel a raison (`env-divergence.ts`). La comparaison porte sur le parc ENTIER, jamais sur la page filtrée (une prod sur une autre instance ne doit pas disparaître), sans archivés ni supprimés ; les empreintes sont gardées en mémoire par `Workflow.hash` et toutes périmées au moindre changement de mapping ou de nom (`WorkflowDivergenceService`). Un tag qui compare (`= prod`, `à déployer`, `prod modifiée`, au niveau de l'exemplaire comme de la famille) **s'ouvre sur l'écart lui-même** (`GET /workflows/:id/divergence`, `divergence-modal.tsx`) : constater QU'il y a un écart ne permet pas de décider, il faut voir CE QUI diffère. Le diff est celui des formes normalisées que hache la clé (`deployForm`, `deployDiff` — domaine pur `deploy-diff.ts`), calculées avec le même contexte que la colonne (`WorkflowDivergenceService.keyContext`) : un écart constaté a toujours au moins une ligne à montrer, et rien de ce que la promotion neutralise n'y passe pour un écart. D'où aussi `workflow-diff.ts` qui compare désormais TOUS les champs d'un nœud et non une liste fermée — un `retryOnFail` ou un `onError` changeait l'empreinte sans jamais apparaître au diff. Il se lit dans le sens de la promotion (avant = la prod aujourd'hui, après = la prod si on y promeut l'exemplaire) : en `behind`, les lignes retirées sont le correctif que la prod PERDRAIT. Les actions suivent le sens — « Promouvoir vers <env suivant> », ou « Voir le correctif en prod » avec la promotion reléguée derrière une confirmation — et ouvrent l'écran de promotion de la page workflow, le SEUL : il y en avait un second, pré-ciblé sur la prod comparée, qui faisait sauter la preprod à qui ne regardait pas la cible. D'où qu'on l'ouvre, il propose la même instance (dev et prod y cohabitent le plus souvent) et l'étape suivante de la chaîne (`GET /env-switcher/promote/:id/defaults`, domaine pur `nextEnv` : premier env déclaré qui dépend de la source ; rien au bout de la chaîne ni pour un env indéterminé) — les deux se changent. Lu sur le miroir local, dont la date est affichée : ouvrir l'écran ne coûte aucun appel à n8n. Pas encore sur Make (`unknown`).
- Le **JSON d'un workflow** se copie ou se télécharge depuis la liste comme depuis ses deux pages (bouton « JSON ») : `GET /workflows/:id/export` repart de n8n — un export sert à être relu ailleurs, le miroir local date au mieux du dernier cron — et retombe sur la copie locale en le DISANT (`stale` + date) quand n8n ne répond pas, plutôt que de refuser l'export ou de livrer un état périmé en silence. Le JSON rendu est débarrassé de l'identité de son exemplaire (id, `versionId`, `meta.instanceId`, état actif, ids de tags — domaine pur `workflow-export-json.ts`) : tel quel, il se réimporte dans n'importe quel n8n par « Import from File » sans se rattacher au workflow source. Les données épinglées en sont **exclues par défaut** (case à cocher) : c'est de la donnée d'exécution réelle, et un export part souvent chez un tiers — assistant IA, ticket. Un scénario **Make** sort par le même bouton, en blueprint TEL QUEL (`blueprint-export.ts`, fichier `.blueprint.json`, « Import Blueprint » chez Make) : il ne porte pas l'identité de l'exemplaire comme le JSON n8n, et ses connexions n'y sont que des ids. La sauvegarde GitHub/Drive, elle, n'a jamais regardé la plateforme — elle lit la table des versions —, et son message de commit dit désormais laquelle (`chore(make): …`).
- Un workflow **neuf** se crée depuis la page Workflows (`POST /workflows`, `workflow-create.service.ts`) : vide et inactif dans n8n — un seul déclencheur manuel (domaine pur `blank-workflow.ts`), et non zéro nœud, pour que l'assistant ait un point d'ancrage où accrocher la suite — puis le tiroir de l'assistant s'ouvre sur « que doit faire ce workflow ? ». Une conversation ouverte sur un workflow encore vide est amorcée par ce message (écrit en dur : la question est toujours la même) et le prompt bascule en mode construction, sinon l'IA commente un contenu qui n'existe pas au lieu de le bâtir. Les nœuds proposés passent par le même chemin que n'importe quelle modification : opérations d'édition, revue en diff, PUT vers n8n.
- Paramètres inertes : n8n **conserve dans le JSON** la valeur des champs que la config courante masque — mapping manuel resté sous `mappingMode: autoMapInputData`, `assignments` d'un nœud Set repassé en mode `raw`, `bodyParameters` avec `sendBody: false`, `jsCode` d'un nœud Code passé en Python… Il ne les exécute pas : toute analyse d'expressions passe donc par `activeParameters(node)` (`packages/core/src/domain/inert-params.ts`) au lieu de `node.parameters`, sinon on juge du code mort (faux `field-unknown`, `expression-missing-node`). Exception : les réécritures (renommage sûr, édition IA) travaillent sur les paramètres complets, pour ne pas laisser de refs périmées si l'utilisateur repasse en mode manuel.
- Findings « normaux / voulus » : règle d'exclusion `FindingIgnore` (module + code, nœud précis ou tous) à **trois portées** : ce workflow (`workflowId`), le même workflow métier dans tous ses environnements (`familyKey`, cf. `workflow-family.ts` — c'est le **défaut de l'UI** : un finding normal en dev l'est aussi en prod, sinon la règle se recrée à chaque env et l'oubli d'un seul fait revenir le bruit), ou partout (les deux à null). Chaque module d'analyse filtre via `FindingIgnoreService.filterIgnored` **avant** persistance (compteurs cohérents) ; gestion et réactivation depuis la page `/finding-ignores`. Une règle est ancrée sur des **identifiants**, pas sur des noms : la portée famille pointe le workflow d'origine (`familyWorkflowId`) et non sa seule `familyKey`, et le nœud visé porte son id n8n en plus de son nom — sans quoi le moindre renommage (celui que propose `optimizer`, par exemple) périmait la règle en silence et faisait revenir le finding déclaré normal. À défaut, l'empreinte du message d'origine sert de dernier chemin d'appariement (domaine pur `finding-key.ts`). Les règles antérieures s'apparient encore par nom et reçoivent leur ancre au premier appariement. Les revues **IA** (`ai-logic-review`, `js-checker`) reçoivent en plus la liste de ce qui est déjà déclaré normal, message et raison compris : le post-filtre suffisait à ne pas l'afficher, mais l'IA le cherchait et le rédigeait à chaque passe.
- Findings affichés **groupés** (`findings-list.tsx`, par nœud par défaut, ou par règle / module / à plat) : les six remarques d'un même nœud Code se corrigent d'une seule réécriture, c'est le nœud et non la ligne qui est l'unité de travail. D'où des actions portées par le groupe autant que par la ligne — « Ignorer » (une règle par (module, code, nœud), dédupliquée) et « Corriger (IA) » (`finding-fix.service.ts`, jumeau de `error-fix.service.ts` : les findings deviennent une conversation pré-alimentée et l'IA répond par une proposition d'édition **revue en diff** avant tout PUT vers n8n ; plusieurs findings d'un même workflow passent dans un seul appel, sinon les propositions s'écraseraient l'une l'autre).
- Contrôles à jouer, **choisis avant de lancer** (bouton « Contrôles » de la page workflow, `check-selection-modal.tsx`) : mode simple (une case par famille — Structure, Fiabilité, Revue IA, Code JS, Naming, Sticky notes, Champs) ou avancé (la règle une à une). Le catalogue est servi par l'API (`GET /check-profiles/catalog`, domaine pur `check-catalog.ts`) : le web ne dépend pas de `@nwm/core`. On enregistre ce qui est **décoché**, jamais ce qui est gardé — une règle ajoutée plus tard est active partout sans rouvrir les profils. Un profil s'applique à un périmètre (`CheckProfile`, portées `family` / `group` / `instance` / `global`) et **le plus précis gagne sans fusionner** : l'UI peut alors nommer l'origine (« hérité de : instance Prod »), là où une fusion aurait obligé à lire quatre profils pour savoir ce qui tourne. La portée n'est pas demandée à chaque fois (domaine pur `check-profile.ts`) : première configuration ⇒ celle de l'app, avec un mot discret ; ensuite ⇒ le workflow, tous environnements confondus ; et **dès que la même sélection existe déjà ailleurs**, on propose de la remonter au palier le plus précis où la répétition se voit — groupe, puis instance, puis application (les profils plus étroits qui disaient déjà la même chose sont retirés, sinon la remontée n'a aucun effet visible). Le décochage n'est pas un filtre d'affichage : la revue IA n'est pas appelée si tout ce qu'elle produit est décoché, et `field-checker` n'échantillonne pas les exécutions — mais l'analyse passe quand même effacer les findings du contrôle retiré. Un lancement porte sa sélection dans le corps de la requête (`{ disabled: string[] }` sur `/verifier/run`, `/js-checker/run`, `/optimizer/analyze`, `/field-checker/run`) : sans elle, l'API résout le profil du workflow — c'est ce qui fait que la vérification de masse depuis `/findings` respecte les mêmes choix.
- IA : **deux fournisseurs**, un seul en service à la fois. Anthropic par le SDK officiel `@anthropic-ai/sdk` (modèle par défaut `claude-sonnet-5`) et Mistral en `fetch` direct (`mistral-medium-latest` — le `large` ne lit pas les images, que le tiroir de chat accepte), le SDK Mistral v2 étant publié en ESM seul quand l'api est compilée en CommonJS. Les analyses de masse enchaînent des dizaines d'appels : un modèle rapide prime sur la finesse. Clé + modèle configurables par fournisseur depuis l'UI (page Modules → Réglages IA, une ligne `AiSettings` PAR fournisseur, `active` désignant celui qui sert), fallback sur `ANTHROPIC_API_KEY`/`ANTHROPIC_MODEL` ou `MISTRAL_API_KEY`/`MISTRAL_MODEL`. Les deux clés cohabitent exprès : basculer parce que l'un est plafonné ne doit pas coûter une ressaisie. Le fournisseur actif est relu à CHAQUE appel (`SwitchingAiAdapter`) et non à l'injection — la DI ne construit qu'une fois, et un choix figé au démarrage imposerait de redémarrer l'api pour changer de fournisseur, c'est-à-dire au pire moment. Deux réglages du port n'ont pas d'équivalent chez Mistral et sont ignorés sans erreur : `effort` et `showThinking` (le `thinking` revient donc vide). Jamais d'appel fetch direct vers api.anthropic.com. Deux réglages par appel (`AiGenerateParams`) : `effort` (`low`/`medium`/`high`) pilote la profondeur de raisonnement — c'est le premier levier de latence, les analyses de masse tournent en `low` — et `maxTokens`, dont le budget **couvre aussi ce raisonnement** : trop juste, la réponse revient tronquée (l'adapter lève alors une erreur explicite au lieu de laisser échouer le `JSON.parse`).
- Secrets uniquement via variables d'environnement (`.env`, cf. `.env.example`) ou réglages en DB jamais renvoyés à l'UI (`MonitoringSettings`, `AiSettings`).
- Authentification : portée par le **front** (`apps/web/src/middleware.ts` + `apps/web/src/lib/auth/`), pas par un module NestJS — la plateforme n'a pas de table utilisateur. Deux méthodes : **Google OAuth** restreint aux domaines de `GOOGLE_ALLOWED_DOMAIN` (obligatoire — sans lui la connexion Google refuse tout le monde ; on exige le claim `hd` ET le suffixe de l'email, donc un Gmail perso est refusé) et **identifiant / mot de passe** d'équipe (`APP_USERNAME` / `APP_PASSWORD`, repli et dépannage). Session = un cookie signé HMAC (`nwm_session`, expiration dans le payload signé). S'y ajoute le **premier login** : sans aucune méthode configurée, le middleware ne sert QUE la page `/setup`, qui crée l'unique compte admin en DB (`AuthSettings`, hash scrypt + secret de session généré, servis au serveur Next par `/auth-settings/bootstrap` — route interne, jamais l'UI). Une installation vierge n'est donc **jamais ouverte** ; seule exception `AUTH_OPTIONAL=1`, posé par `docker-compose.override.yml` (dev local). L'état DB est mis en cache 10 s côté Next (`db-auth.ts`) et une API muette retombe sur la config d'env : pas de plateforme verrouillée par une panne du backend. Détails et mise en place : [docs/authentification.md](docs/authentification.md).
- Le middleware garde les pages **et** le proxy `/backend/*` : une page sans session part sur `/login`, un appel `/backend/*` reçoit un 401 JSON (l'UI l'affiche, elle ne suit pas une redirection HTML). C'est aussi lui qui injecte `x-api-token` vers l'API — d'où `NEXT_PUBLIC_API_URL` à laisser vide dès que `API_ACCESS_TOKEN` est posé (en direct, le navigateur n'a pas le jeton) — **et** `x-user-email`, l'identité connectée, qui signe les actions humaines côté API (qui a marqué une erreur comme traitée). Ces deux en-têtes sont effacés puis reposés par le middleware : ce que le navigateur envoie n'est jamais repris, sinon on pourrait se faire passer pour un autre.
- **Mémoire des listes** (`apps/web/src/lib/list-memory/`) : on retrouve une liste comme on l'a laissée — filtres, recherche, vue et switches de la page, tri, page, taille de page, largeurs, colonnes affichées et leur ordre. Rangé dans le localStorage (`nwm.list.<page>…`), donc par navigateur : rien côté API, rien qui suive d'un appareil à l'autre. Trois points d'accroche, et aucun code par page au-delà : `usePersistedState` remplace le `useState` d'un filtre ; `useTable` de `list-memory` remplace celui de `@refinedev/antd` (tri, page, taille — les filtres restent aux contrôles de la page, retenus aux deux endroits ils finiraient par se contredire) ; `ResizableTable` retient largeurs et colonnes, plus tri et page d'une table LOCALE (sans `onChange`). Le menu « Colonnes » (⚙ au coin de l'en-tête) apparaît dès 4 colonnes nommées hors tables `small`, et porte « Réinitialiser la vue », qui efface tout ce que la page a retenu. Trois règles : la mémoire se lit au PREMIER rendu (les pages se montent après `InstanceScopeGate`, côté navigateur) et part dans la première requête, jamais dans une seconde ; **l'URL gagne** — Refine préfère déjà ses paramètres, et un filtre adossé à un paramètre (`urlParam`) ne se restaure pas quand le lien le porte ; on n'écrit qu'au GESTE, jamais à l'ouverture, donc un lien partagé n'écrase pas la mémoire de qui l'ouvre (comparer à l'état du montage et non sauter le premier passage : React rejoue les effets deux fois en dev). Ce qui est relu est validé (`list-memory.ts`, pur et testé) : une colonne disparue, un tri refusé par l'API ou une page hors du total sont oubliés sans erreur. Le filtre d'instance reste global (`nwm.instance-scope`), hors de cette mémoire.
- **Listes sur mobile** : sous le breakpoint `md`, `ResizableTable` se rend en **lignes dépliables** (`components/mobile/mobile-table.tsx`) dès 4 colonnes — un tableau de sept colonnes dans 360 px ne se lit qu'en défilant de côté. La ligne repliée montre la première colonne nommée (et des badges), le tap déplie les autres en « libellé : valeur », puis les actions de ligne et l'éventuel `expandedRowRender`. Mêmes colonnes (choix du menu compris), mêmes données, même pagination — celle de Refine repasse par le `onChange` du tableau, sans tri ni filtre. Les cases à cocher cèdent la place à l'appui long (mode sélection, où le tap coche). Par table : `mobileLayout` (`title`, `badges`, `hidden`, par identité de colonne — domaine pur `mobile-table-layout.ts`) ou `mobile={false}` pour garder le tableau. La page Workflows a son propre rendu (`app/workflows/mobile/`), bâti sur les mêmes briques (`MobileRow`, `mobile-gestures.ts`). Autour des listes, deux briques de plus : `useIsMobile` (seuil unique `md`) et `HeaderActions` (boutons d'en-tête côte à côte sur desktop, action principale + menu « ⋯ » sur mobile — Monitoring en alignait six). Une `Card` dont l'en-tête porte des boutons les passe dans son corps sur mobile (`ResponsiveCard`), sinon le titre est mangé (Couverture, Performance, Catalogue des nœuds) ; une page à plusieurs filtres les range dans `MobileFilterBar` (Couverture, Workflows). Un tableau de champs ÉDITABLES ne se replie pas comme une liste (le titre serait un champ, et le tap le focaliserait au lieu de déplier) : les environnements de la page Modules s'empilent en blocs, mêmes champs écrits une seule fois pour les deux dispositions (`env-chain-card.tsx`).
- **Fiche d'un workflow** : le schéma et l'inventaire des nœuds y sont deux ONGLETS (`components/workflow-structure.tsx`, `GET /workflows/:id/view` chargé à l'ouverture de l'onglet). Ils vivaient sur `/workflows/view/:id`, une page à part : on quittait la fiche pour regarder le workflow, et les findings s'affichaient des deux côtés. Cette route redirige désormais vers `…/show/:id?tab=graph`, et `?tab=` ouvre n'importe quel onglet depuis un lien. Les environnements du workflow métier sont eux aussi des onglets (`env-links.tsx`) : un env déclaré SANS exemplaire y figure en grisé — son absence est une information — et le clic ouvre l'assistant d'env directement sur « copier vers cet env » (`startCopyTo`). Les actions passent par `ActionBar` en mode `always` : quatre sous la main (Vérifier, Assistant IA, Ouvrir dans n8n, plus l'onglet Schéma), le reste sous « ⋯ ». Le temps gagné par exécution est un RÉGLAGE, pas une mesure : ligne discrète, édition au clic — en champ ouvert, il se lisait comme un temps mesuré. La synchro depuis n8n est une ICÔNE au coin de la carte (le rafraîchissement d'un navigateur), la documentation se lit en ouvrant son onglet — qui la charge, et propose de la générer quand elle manque —, et « Données réelles » (ex-« Champs observés », `execution-samples-panel.tsx`) est l'onglet qui montre ce que les nœuds ont vraiment sorti : la matière que `field-checker` compare aux expressions. L'assistant IA n'occupe plus un bouton de la rangée : icône au coin sur desktop, bouton flottant sur mobile, et glissé vers la gauche depuis la droite de l'écran (`use-swipe-open.ts`, qui laisse les ~28 px du bord au geste « retour » du système).
- **Page Aide** (`/aide`, en pied de menu) : une astuce par fonction, chacune avec sa vignette animée — l'écran rejoué en HTML/CSS, pas une capture, qui vieillirait au premier changement d'UI. Ajouter une astuce : une entrée dans `app/aide/tip-catalog.ts` (`module` la grise quand il est désactivé) et une scène dans `tip-scenes.tsx` (étapes `hp-a1`→`a5`, curseur `Cursor`, timings communs dans `aide.css`). Au repos une carte montre l'image finale et ne s'anime qu'au survol ; le catalogue alimente aussi la palette ⌘K (groupe « Astuces », seulement quand on cherche).
- **Menu sur mobile** (sous le breakpoint `lg`, seuil du sider Refine) : une barre du haut (`MobileTopBar`, slot `Header` de `ThemedLayoutV2`) porte le titre à gauche et le bouton ☰ à droite, qui ouvre le tiroir du sider par `useThemedLayoutContext`. Le bouton que `ThemedSiderV2` pose de lui-même — fixé à gauche, 64 px du haut, par-dessus la page — est masqué (`.app-sider` dans `globals.css`) : il recouvrait le premier contrôle de chaque écran. Un élément collant de page se pose sous la barre (`MOBILE_TOP_BAR_HEIGHT`).
- **Installation (PWA)** : la console s'installe comme une app (bouton « Installer l'app » en bas du menu, `install-app-button.tsx` — masqué une fois installée, et sur iOS il explique le geste puisque Safari ne tire jamais `beforeinstallprompt`). Manifeste, icônes et service worker vivent dans `apps/web/public/` et sont **laissés passer sans session** par le middleware (`PWA_PATHS`) : le navigateur va chercher le manifeste sans cookie, il recevrait sinon la page `/login`. Le service worker ne met en cache QUE les assets immuables du build et la page hors-ligne — jamais `/backend`, `/auth` ni un écran de la console : les données viennent de l'API derrière la session, et un écran servi du cache montrerait l'état d'hier, ou celui d'un utilisateur déconnecté. Les icônes sont générées par `apps/web/scripts/generate-icons.mjs` (pur Node : aucun rasteriseur au build, et une icône PWA doit être du PNG). Deux endroits à ne pas oublier hors du code : `public/` n'est pas tracé par `output: 'standalone'` (COPY dans le Dockerfile) et n'est pas monté en dev (bind mount dans `docker-compose.override.yml`).
- L'API est protégée séparément par `ApiTokenGuard` (`apps/api/src/common/auth/`, APP_GUARD) : sans `API_ACCESS_TOKEN` elle reste ouverte (dev), sinon elle n'accepte que le jeton du proxy. Une route appelée par un système tiers se marque `@PublicRoute()` — c'est le cas du heartbeat `POST /monitoring/beat/:token`, qui a son propre secret dans l'URL.
